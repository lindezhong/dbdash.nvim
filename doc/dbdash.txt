1. INTRODUCTION                                                 *dbdash-intro*

dbdash.nvim runs a query on an interval and shows the result in a buffer as a
table or a terminal chart. It is written in pure Lua for Neovim 0.12+ and has
no external dependencies: no Python, no database command-line tools. SQLite
is used through LuaJIT FFI and the system `libsqlite3`.

Each config file (YAML) describes one dashboard: the database, the query (a
Jinja2 template) and how to show the result.

==============================================================================
2. SETUP                                                        *dbdash-setup*

Install with any plugin manager. Calling setup() is optional; these are the
defaults: >lua

  require("dbdash").setup({
    mappings = true,       -- global keys, see below
    countdown_interval = 10000,          -- ms between countdown updates
    countdown_position = "right_align",  -- "eol", "overlay"
    style = {},            -- your style sheet for every dashboard:
                           -- selector -> properties, |dbdash-css|
    ticks = "nice",        -- axis ticks: "nice" or "linear"
    register = {},         -- custom chart styles and canvases
    sidebar = {
      width = 30,          -- columns, or "30%" of the editor width
      position = "left",   -- "left" | "right"
      dir = nil,           -- directory to list: nil = current directory,
                           -- a path, or a function returning one
      pattern = { "*.yaml", "*.yml" },               -- files to list
      exclude = { "*.schema.yaml", "*.schema.yml" }, -- files and
                           -- directories to skip, e.g. "node_modules"
      keys = { select = "<CR>", stop = "t", refresh = "r", close = "q" },
      cursorline = "line", -- "line": the usual CursorLine; "name": only the
                           -- name, see |dbdash-highlights|; false: none
    },
    dashboard = {
      open = "current",    -- where :DbDashStart shows a dashboard:
                           -- "current" | "vsplit" | "split" | "tab"
      pause_hidden = true, -- no queries while not on screen, see below
      keys = { modify = "a", show_args = "A", refresh = "r",
               reset = "R", show_sql = "s", export = "e",
               describe = "K" },
    },
    popup = {              -- :DbDashShowSQL and the other floats
      border = "rounded",  -- any 'winborder' value or a list of chars
      max_width = 120,     -- columns or "N%"
      max_height = "100%", -- rows or "N%"
    },
    defaults = {           -- used when a config file does not say
      interval = "30s",    -- refresh interval
      timeout = "30s",     -- query timeout (URL `timeout` wins)
      connect_timeout = "10s",  -- (URL `connect_timeout` wins)
      max_rows = 10000,
      history = 20,        -- queries kept for |:DbDashStatus|
    },
    errors = {             -- failed refreshes, see |dbdash-errors|
      notify = "once",     -- "once" | "always" | "never"
      backoff = 8,         -- retry after at most interval x 8; 1 = off
    },
    lua = {                -- configs with Lua code, see |dbdash-lua|
      confirm = true,      -- ask once per config before running them
      trusted_dirs = {},   -- configs under these directories run unasked
      max_callbacks = 100, -- dbdash.run() calls in one refresh, all levels
      max_callback_depth = 10,  -- dbdash.run() nesting, |dbdash-callback|
    },
    push = {               -- push sources (exec://, luastream://, webhook://)
      max_queue = nil,     -- items waiting per panel: unlimited; a number
                           -- keeps only the newest (|dbdash-push|)
      max_record = "1MB",  -- longest item; longer ones are cut there
    },
  })
<
Only the options you pass change; nested tables merge with the defaults, while
lists (`pattern`, `exclude`) replace them. Invalid or unknown options are
reported with their path (e.g. "sidebar.width: invalid size") and fall back
to the default.

Sizes are a number of cells or a percentage string of the editor width or
height ("30%"), computed when the window opens.

Keys: set a key to `false` to remove it. `mappings` is `true` (all global
keys), `false` (none) or a table that changes some of them: >lua
  mappings = { start = "<leader>ds", refresh = "<leader>dr",
               stop = "<leader>dt", list = "<leader>dl",
               sidebar = "<leader>dd" }  -- the defaults; false removes one
<
Global keys already mapped by you are not overwritten. `ticks` and `register`
are described in |dbdash-styles|.

All appearance is in style sheets (|dbdash-css|); `style` is yours, between
the default sheet and each dashboard's own. For example, every line chart on
a quadrant canvas, plots 10 rows high and the countdown in every header: >lua
  style = {
    ["chart.line"] = { canvas = "quadrant" },
    plot = { height = 10 },
    ["header countdown"] = { display = "block" },
  }
<

Errors                                                         *dbdash-errors*

A config file is checked when it loads, with everything that can be known
then: the YAML, the fields and their types, the arguments, the database
(its type or URL scheme, the URL's ${NAME} variables and parameters, the
driver's `database.options`: an unknown option is an error), the chart
types, the style sheets (properties, renderer, canvas and palette names),
the thresholds and the grid. A problem is reported with its line and
column, and the dashboard does not start: >
  config error: board.yaml:7:9: unknown chart type 'radar'
<
What depends on templates is checked when it runs (the rendered SQL, curl
command or OpenAPI document). Every error reads the same way: the driver,
the phase, where (a file and line, for templates and Lua) and why: >
  sqlite query error: no such table: orders [SQLITE_1]
  template error: board.yaml:11: 'missing' is undefined
<
When a refresh fails, the error has a phase: template (the query
template), connect, tls, auth, query (the database rejected the query, e.g.
a SQL syntax error, or the result is not rows, |dbdash-result|), transform
(the `query.transform` script failed or did not return rows), timeout
(`connect_timeout` + `timeout` elapsed; the query is stopped on the server
too, |dbdash-cancel|) or decode. Then:

- the last good result stays on screen, with the error as a red `✗` line
  above it (with panels: in the panel's header);
- `errors.notify = "once"` notifies when an error first appears or changes,
  "always" on every failure, "never" not at all (it still shows in the
  dashboard and in |:DbDashStatus|);
- consecutive failures of a database back off: after the n-th the next try
  waits interval x 2^(n-1), at most interval x `errors.backoff` (1x, 2x,
  4x, 8x, 8x...). The status shows "retrying" and |:DbDashStatus| the count
  and the next try; the top-level interval (|dbdash-interval|) skips a panel
  that is backing off. A source that sends data (|dbdash-push|) does not
  back off: a failed item is that item only, the next one replaces it;
- `r` / |:DbDashRestart| tries again right away;
- the first successful refresh clears the error and returns to the normal
  interval.

Health checks                                                  *dbdash-health*

`:checkhealth dbdash` checks the plugin itself: Neovim and LuaJIT, the
options of the last setup() call, and the passwords file
(|dbdash-passwords|). What a database needs is checked only for that
database:

  :checkhealth dbdash.sqlite     the SQLite library and its version
  :checkhealth dbdash.postgres   the driver and the system CA store (needed
               dbdash.mysql      for tls=verify-ca / verify-full without ca=)
               dbdash.mssql
               dbdash.redis
               dbdash.cassandra
  :checkhealth dbdash.mongodb    the same, plus the DNS name servers used by
                                 mongodb+srv://

`:checkhealth dbdash*` runs all of them.

3. COMMANDS                                                  *dbdash-commands*

:DbDashStart[!] {config} [{name}={value} ...]                   *:DbDashStart*
    Start the dashboard for {config}, or switch to it when it is already
    running. It opens in the current window, or in a split or tab with
    `dashboard.open` (|dbdash-setup|); a dashboard already visible is jumped
    to. Arguments after the file set query arguments for this session
    (|dbdash-arguments|): `name=value` every argument of that name,
    `<panel>.name=value` one panel's own. With [!], every argument is asked
    for interactively; without it only `required` arguments without a value.

:DbDashRestart                                                *:DbDashRestart*
    Run the current dashboard's query now and restart its countdown. A
    query still running is cancelled and the new one starts at once (the
    same happens when an argument changes, |dbdash-cancel|); timer
    refreshes that come while a query runs are skipped instead.

:DbDashStop [{config}]                                           *:DbDashStop*
    Stop a dashboard (default: the current one) and close its buffer.
    Closing the dashboard's last window (`:q`, `:close`, `:only`,
    `:tabclose`) or deleting its buffer (`:bdelete`) stops it the same way;
    only hiding it pauses it (|dbdash-pause|).

:DbDashList                                                      *:DbDashList*
    List running dashboards.

:DbDashStatus                                                  *:DbDashStatus*
    Show the current dashboard's title, config, global refresh (the
    top-level `interval`) and, for each panel, its database, next refresh
    and last queries (duration, rows, errors, skipped refreshes;
    `defaults.history` of them, 20 by default); for a push source its state
    and items received, processed, queued and dropped (|dbdash-push|).

:DbDash                                                              *:DbDash*
    Open the sidebar: the *.yaml / *.yml files of the current directory and
    its subdirectories as a tree (see `sidebar` in |dbdash-setup| for the
    directory, globs and width). Files show `●` when their dashboard runs,
    `◐` when it is paused (see |dbdash-pause|) and `○` otherwise;
    directories show `▸` (collapsed) or `▾` (expanded) and stay expanded
    when the sidebar is reopened. Hidden directories and names matching
    `sidebar.exclude` (by default `*.schema.yaml`) are not listed; without
    config files the list says so. The cursor line is your usual
    'cursorline'; `sidebar.cursorline = "name"` marks only the name (when an
    underlined CursorLine would turn partly green under ●), false hides it.

                                                                *dbdash-pause*
A dashboard that no window of the current tab page shows (you switched the
window to another buffer, or it is only in another tab page) pauses: no
queries, no countdown. Closing its last window is not hiding it: that stops
the dashboard like |:DbDashStop| (the sidebar shows `○`, not `◐`), except
while Neovim exits or a session loads. A window that shows it counts even
when the cursor is in another window. When it is shown again, it refreshes
right away if its next refresh is due, and otherwise continues the
countdown. Set
`dashboard.pause_hidden = false` to keep hidden dashboards refreshing, or
`show.refresh_hidden: true` for some panels: they keep refreshing on their
interval (and with the top-level `interval`) while the dashboard is paused,
and still notify thresholds and errors.

:DbDashClose                                                    *:DbDashClose*
    Close the sidebar.

:DbDashShowVariables                                    *:DbDashShowVariables*
    Show the current dashboard's arguments and values (a panel's own
    argument whose name another argument has too as `<panel>.name`).

:DbDashModifyVariable                                  *:DbDashModifyVariable*
    Pick an argument and enter a new value.

:DbDashUpdateVariable {name} {value}                   *:DbDashUpdateVariable*
    Set an argument directly: {name} sets every argument of that name (the
    shared one and each panel's own), `<panel>.name` only that panel's.

:DbDashResetVariables                                  *:DbDashResetVariables*
    Reset all arguments to their defaults.

:DbDashShowSQL                                                *:DbDashShowSQL*
    Show the rendered query in a floating window ("q"/<Esc> close, "y" yank),
    followed by the rendered `query.transform` when there is one.

:DbDashDescribe                                              *:DbDashDescribe*
    Show a description (|dbdash-description|) in a floating window, as
    Markdown: the dashboard's with the cursor on the header line, the
    panel's with the cursor on a panel, both in a one-chart dashboard;
    elsewhere pick one. "q"/<Esc> close, "y" yank. `K` in a dashboard.

:DbDashExport[!] [{format}] [{file}]                          *:DbDashExport*
    Export the result of the current dashboard (with panels: the one under the
    cursor, or pick one) as `csv`, `tsv`, `json` or `markdown`; without
    {format} pick one. Without {file} the text goes into the unnamed register,
    or the one given before the command (`"x:DbDashExport csv`, `"xe`). An
    existing {file} is only overwritten with [!]. The whole result (after
    `query.transform`) is exported (not the truncated cells): NULL is empty in
    csv, tsv and markdown and `null` in json; binary values are `\x` hex.

:DbDashStyle {type} [{renderer}]                                *:DbDashStyle*
:DbDashStyle canvas {name}
:DbDashStyle set {selector} {property} {value}
:DbDashStyle reset
    Change the current dashboard's style at run time (the highest place of the
    cascade, |dbdash-css-cascade|) and re-render its cached data without
    querying again. `:DbDashStyle line quadrant` shows the panel under the
    cursor as a line chart on a quadrant canvas, `:DbDashStyle bar vertical`
    as vertical bars, `:DbDashStyle canvas block` changes its canvas (rules
    on that panel's `chart`). `set` adds a rule for the whole dashboard:
    `:DbDashStyle set value color DiagnosticOk`, `:DbDashStyle set dashboard
    grid-template-columns 3` (the value is JSON when it parses as JSON:
    numbers, true, lists). `reset` drops them all. They last until the
    dashboard stops. Without arguments it shows the panel's renderer and
    canvas.

:DbDashInspect [{element}]                                    *:DbDashInspect*
    Inspect the element under the cursor (a panel, its title line, argument
    line or chart), or the nearest {element} from there (`:DbDashInspect
    series`): its path in the tree (|dbdash-css-elements|), the rules that
    match it with their origin and specificity, its computed style, its box
    and highlight group, and its children. The box is highlighted in the
    dashboard until the cursor moves.

:DbDashTrust [allow|deny|remove] [{config}]                    *:DbDashTrust*
    Decide about a config that runs Lua (default: the current dashboard's)
    without the question: `allow` (default) trusts it with its current
    files, `deny` refuses it, `remove` forgets the decision so the question
    comes back. See |dbdash-lua|.

:DbDashMksession[!] [{file}]                                *:DbDashMksession*
:Mksession[!] [{file}]                                            *:Mksession*
    Write a session. Dashboard buffers are named `dbdash://<config path>` and
    are restarted (with default arguments) when the session is loaded. The
    `mksession` command-line abbreviation points here. Any other :mksession
    restores dashboards the same way, also when 'sessionoptions' lacks
    "blank". To also keep changed arguments, see |dbdash-session-state|.

==============================================================================
4. MAPPINGS                                                  *dbdash-mappings*

Defaults; all keys can be changed or removed with `mappings`,
`dashboard.keys` and `sidebar.keys` (|dbdash-setup|).

Global:

  <leader>ds   :DbDashStart
  <leader>dr   :DbDashRestart
  <leader>dt   :DbDashStop
  <leader>dl   :DbDashList
  <leader>dd   :DbDash

Dashboard buffer (`dashboard.keys`: modify, show_args, refresh, reset,
show_sql, export, describe):

  a   modify an argument          A   show arguments
  r   refresh now                 R   reset arguments
  s   show the rendered query     e   export the result
  K   show the description (|:DbDashDescribe|)

Set a key to false to leave it unmapped, and map the command yourself: >lua
  require("dbdash").setup({ dashboard = { keys = { describe = false } } })
  vim.keymap.set("n", "<leader>dk", "<Cmd>DbDashDescribe<CR>")
<

Sidebar (`sidebar.keys`: select, stop, refresh, close):

  <CR>  on a file: open or start its dashboard beside the sidebar;
        on a directory: expand or collapse it
  t     stop it                   r   refresh it
  q     close the sidebar

5. CONFIG FILES                                                *dbdash-config*

>yaml
  database:
    url: "postgres://user:pass@host:5432/db?tls=require&timeout=5s"
    type: postgres          # optional, inferred from the url scheme
    options: {}             # driver options
  query:
    sql: |
      SELECT ...
    transform: |            # optional Lua reshaping the result
      return rs             # (|dbdash-transform|)
    autoescape: false       # render {{ x }} as SQL literals
    max_rows: 10000
    timeout: 30s
    args:
      - name: min_age
        type: number        # string | number | int | boolean | list | map
        default: 18
        required: false
        show: true
        description: "Minimum age"
        choices: [18, 30, 50]
  show:
    type: table             # table | line | area | bar | histogram |
                            # boxplot | heatmap | bubble | pie | scatter |
                            # stat | text
    title: "Users"
    interval: 60s           # s, m, h or ms
    args_show: false        # argument values above the chart
  style:                    # how it looks: a style sheet (|dbdash-css|)
    header countdown: { display: block }
<
Top-level fields: `database`, `query`, `show` (one chart) or `panels`
(several charts, |dbdash-panels|), `args` (shared arguments), `interval`
(|dbdash-interval|), `style` (|dbdash-css|), `title` and `description`.
Durations are numbers of seconds or strings with a unit: "500ms", "30s",
"5m", "1h".

`show` says what to show: the chart type, its columns, titles and the options
that change what is drawn (sorting, stacking, thresholds, ...). How it looks,
the grid included, is in style sheets (|dbdash-css|); a config that still has
an appearance field (`layout`, `show.span`, `show.height`, `show.canvas`,
`show.colors`, `show.style`, ...) is an error that says where it went.

Where a field is written says what it applies to, with one chart or many:

  dashboard-wide       top-level bare fields: `interval`, `args`, `style`,
                       `panels`, `title`, `description`
  per panel, with a    the top-level `database`, `query` and `show`
  top-level default    sections: `database`; `query.timeout`, `max_rows`,
                       `autoescape`; `show.interval`, `args_show`,
                       `refresh_hidden`, `thresholds`, `axes`, ...
  one panel only       `query.sql`, `transform`, `args`; `show.type`,
                       `title`, `description`, `column_list`, the
                       `*_column` fields, `x_label`, `y_label`; a panel's
                       own `style`

Without `panels` the top level is the only panel, so every field is written
there. With `panels` each panel is its top-level `query` and `show` with its
own fields over them (mappings merge key by key, lists are replaced), and
fields of one panel only are an error at the top level. A panel's `database`
replaces the top-level one as a whole (its `options` and `password_cmd`
too). Both kinds of config validate each panel the same way.

`query.max_rows` caps the rows read; `query.timeout` defaults to the URL's
`timeout`. Values a config leaves out (interval 30s, max_rows 10000, timeout
30s) come from `defaults` in |dbdash-setup|. Fields the plugin does not use
are ignored; invalid values of known fields are reported with their line and
column. The full list of fields is in `example/dbdash.schema.yaml`
(|dbdash-examples|).

Table options: `column_list: [{column, alias, width, height, align, format,
thresholds}]` picks, names, sizes and formats columns (a column's `width`
fixes its width, `height` the most lines a cell takes; `format` is a Python
format for numbers: "{:,.2f}", "{:.1%}"); `sort` orders the rows (a column,
or `{ column, order: asc | desc }`; NULLs last); `row_thresholds: { column,
steps, below }` gives whole rows a class by one column's value. Long cells
wrap inside their column; newlines in a value start a new line. When the
window is narrower than the table, the widest text columns shrink first and
their cells wrap more. The rest is style: `table { border, line-clamp }`,
`header`, `row`, `cell { width, height, padding, white-space, word-break,
vertical-align, text-overflow }`, `cell.null { content }`, `rule`
(|dbdash-css-elements|). `example/charts/table.yaml` shows each option.

Refresh intervals                                            *dbdash-interval*

`show.interval` is a panel's period: the panel shows new data at most once
per period. A database is queried once per period (a refresh that comes
while its query still runs is skipped). A source that sends data
(|dbdash-push|) sends whenever it has something: the first new result of a
period shows at once, a later one at the start of the next period, so a
fast source does not redraw for every item.

A panel's interval is its own `show.interval`, else the top-level
`show.interval`, else the top-level `interval`, else `defaults` in
|dbdash-setup| (30s). The top-level `interval` is a refresh of every panel
at once: when it elapses every panel gets a new period, and each one's own
count starts again from there (a panel's deadline and the top-level one at
the same moment are one refresh). A panel whose interval is the top-level
one or longer only ever refreshes with everything else. >yaml
  interval: 10m        # every panel, every 10 minutes
  show:
    interval: 1m       # each panel's default
  panels:
    - show: { interval: 10s }   # this one every 10 seconds too
    - show: {}                  # every minute
<
Header                                                         *dbdash-header*

`title` at the top level puts a header line above the charts (so does a
description's `ⓘ`, |dbdash-description|, and a shown header countdown): the
title on the left, the countdown to the next refresh of every panel (the
top-level `interval`, which it needs) on the right, "…" while that refresh
runs. Countdowns are elements hidden by default: `header countdown` is the
dashboard's, `panel countdown` (or just `countdown`) each chart's own. Their
`content` is the format: `{time}` is the seconds left and `{clock}` the time
as m:ss (h:mm:ss from an hour): >yaml
  title: "Sales overview"
  interval: 10m
  style:
    header countdown: { display: block, content: "all in {clock}" }
<
The title also names the dashboard in threshold notifications (for a chart
without `show.title`), the panel picker, |:DbDashStatus| and
`meta.dashboard_title`.

Descriptions                                              *dbdash-description*

The top-level `description` describes the dashboard, `show.description` one
chart (it belongs to one panel). Both are templates (|dbdash-templates|),
rendered when shown, and their result is Markdown: >yaml
  description: |
    # Sales overview
    The last **{{ args.hours }} hours**{% if args.region %}, region
    `{{ args.region }}`{% endif %}.

    | Source         | Lag   |
    |----------------|-------|
    | orders replica | 5 min |
<
They are not drawn in the dashboard: `ⓘ` after a title says there is one
(the header's for the dashboard's; a panel's own title for a panel's; in a
one-chart dashboard the header's for either; the icon is the `content` of
`description-icon`), and `K` (|:DbDashDescribe|) shows it in a float with
Markdown highlighting (treesitter; the Vim syntax when Neovim has no
markdown parser), concealed markup and wrapped lines. A chart's description
sees what its query sees: `args` with its own arguments and `meta` with its
panel and database. The dashboard's sees the shared arguments and `meta`
without the panel fields (`db_*` of the top-level database). Imports and Lua
work as in queries, and Lua in a description asks for trust like any other
(|dbdash-lua|), but a description cannot assign arguments
(|dbdash-assign-args|): showing it changes nothing. The SQL filters quote for
the panel's database, in the dashboard's description for the top-level one
(SQLite's quoting without one).

Examples and schema                                          *dbdash-examples*

The `example/` directory of the plugin has runnable configs, one directory per
topic (the sidebar shows them as a tree):

  charts/       style sheets (css.yaml), and one file per chart type with
                every renderer and option, one panel each
  dashboards/   several panels in a grid (multi_panel.yaml), a grid laid
                out with CSS Grid properties (grid.yaml)
  templates/    arguments; every statement, filter, test, function and
                method; SQL filters and autoescape; macros; extends,
                include and import; Lua in templates; every meta field
  lua/          a lua:// source, query.transform, store, callbacks, run
                records
  push/         luastream://, exec:// and webhook:// (|dbdash-push|)
  databases/    a SQLite file; after `make it-up` (the test services in
                docker): postgres, mysql, redis, mongodb, cassandra, mssql
                and http
  connections/  after `make it-up`: TLS modes, passwords outside the
                config, cancelling a slow query; an HTTPS API (github.yaml,
                needs network)

The others use an in-memory SQLite database and run as they are. Those that
run Lua or a script ask for trust first (|dbdash-lua|).

`example/dbdash.schema.yaml` is a JSON Schema for config files. It lists every
field, every style property and the URL format of each database;
|dbdash-schema| shows it, with a tag for every field
(`:help dbdash-schema-show.interval`). Editors using yaml-language-server
validate and complete a config that starts with: >yaml
  # yaml-language-server: $schema=/path/to/example/dbdash.schema.yaml
<
The sidebar does not list `*.schema.yaml` files (the default
`sidebar.exclude`).

Multiple panels                                                *dbdash-panels*

One config can hold several charts in a grid: >yaml
  database: { url: "postgres://..." }   # default; a panel may set its own
  interval: 5m      # refreshes every panel (|dbdash-interval|)
  args:             # shared arguments: every panel can use them
    - name: region
      default: EU
  style:            # the dashboard's style sheet
    dashboard: { grid-template-columns: 2 }
    countdown: { display: block }
  panels:
    - id: orders
      query: { sql: "SELECT ..." }
      show: { type: line, title: Orders, interval: 30s }
      style:        # this panel's own rules
        panel: { grid-column: "span 2" }
    - query: { sql: "SELECT ..." }
      show: { type: table, title: Latest }
<
Panels flow left to right and wrap; `panel { grid-column: "span 2" }`
widens a panel over several columns, and a single panel under `panels` is a
grid too (|dbdash-layout| for sizes, rows, areas and placement). `id` names
a panel for its arguments (|dbdash-arguments|) and for style sheets
(`#orders`). In the dashboard, `s` and |:DbDashStyle| act on the panel under
the cursor (or ask which one); `r` refreshes all panels.

Each panel queries its own database: `panels[].database` if it sets one,
else the top-level `database`, which is only a default (a one-chart config is
the same rule with the top level as its only panel). The top-level `database`
can be left out when every panel sets one; a panel with neither is an error.
Panels of different database types can share a dashboard: >yaml
  database: { url: "postgres://..." }   # default
  panels:
    - query: { sql: "SELECT ..." }      # postgres
    - database: { url: "redis://cache" }
      query: { sql: "INFO memory" }     # redis
<
The SQL filters, autoescape and the `meta.db_*` values follow the panel's
database.

Grid layout                                                    *dbdash-layout*

The grid is CSS Grid, written in style sheets: the `dashboard` element is the
grid container and each `panel` a grid item. Panels are placed by area, by
row and column, or in order into the next free cells. >yaml
  style:
    dashboard:
      grid-template-columns: [1fr, 2fr, 30]  # or "1fr 2fr 30", or 3
      grid-template-rows: [auto, 20, 1fr]    # later rows: grid-auto-rows
      grid-auto-rows: auto                   # (default auto)
      column-gap: 2                          # (default 2)
      row-gap: 1                             # blank lines (default 1)
      grid-template-areas:                   # "." is an empty cell
        - "trend trend kpi"
        - "table table kpi"
    "#trend": { grid-area: trend }           # by area name
  panels:
    - id: trend
      query: { sql: "..." }
    - query: { sql: "..." }
      style:
        panel: { grid-row: "1 / span 2", grid-column: 3 }   # by position
    - query: { sql: "..." }
      style:
        panel: { grid-column: "span 2" }     # next free cells
<
Container (`dashboard`): `grid-template-columns`, `grid-template-rows`,
`grid-auto-rows`, `column-gap`, `row-gap`, `grid-template-areas`. Items
(`panel`): `grid-area`, `grid-row` and `grid-column` (N, "span M" or
"N / span M"), `justify-self`, `align-self`. A chart's smallest plot is
`plot { min-height }` (default 8) and its full plot `plot { height }`
(default 15).

Tracks:
  integer          a fixed size: display columns, or lines for rows
  "N%"             columns: a share of the width
  "Nfr"            a share of what is left (columns at least 10 wide, rows
                   at least their panels' min-content)
  auto             columns: 1fr; rows: minmax(min-content, max-content)
  min-content      rows: as tall as the panels with their smallest plot
                   (`plot { min-height }`, 8)
  max-content      rows: as tall as the panels with their full plot
                   (`plot { height }`, 15); tables, stat and text charts
                   have one height
  "minmax(a, b)"   at least a, at most b (b may be fr)

Rows are sized like CSS: each row gets its panels' min-content, the lines of
the window that are left grow the rows up to their limit (auto rows up to
max-content, equally), and fr rows share what remains. Nothing is squeezed
below its min-content: a grid taller than the window makes the buffer longer,
and you scroll. A panel in a fixed or fr row fills its cell (its plot grows
with the row, unless `plot { height }` is set). A panel over several rows
that needs more than they give adds the difference to those rows.

Placement follows CSS: panels with an area or a row and column go first,
panels with only a row or a column go into the first free place there, and
the rest flow in order into the next free cells. An unknown area, areas that
are not rectangles, panels that overlap and positions past the last column
are errors, reported with the line of the rule at fault. A rule added with
|:DbDashStyle| that breaks the grid shows its error above the panels.

Chart fields:                                                  *dbdash-charts*

`show` holds what to show; the style rules that matter most for each type
follow the ";" (all of them: |dbdash-css-elements|).

  line       x_column, y_columns [{column, label}] (or y_column, or
             series_column for long data), span_gaps, axes.{x_axis,
             y_axis}.{title, min_value, max_value, format, scale, ticks},
             mark_lines, mark_points, trend_line; series { color, curve,
             fill }, point { display, content }, grid.x / grid.y, legend
  area       the line fields, stacked (true or percent)
  bar        x_column, y_column (or y_columns, series_column), stacked,
             sort, top, axes.y_axis.{min_value, max_value, format},
             mark_lines; series { color }, bar { width, gap }, value
             { display, position }
  histogram  value_column, bins, bin_width, bin_range, cumulative,
             normalize, mark_lines; series, value
  boxplot    category_column, value_column, whiskers; series, outlier,
             mean, value
  heatmap    x_column, y_column, value_column, scale_min, scale_max; chart
             { color-scale, color-steps }, value, legend
  scatter    x_column, y_column, color_column, trend_line, axes,
             mark_lines; series, point { content }
  bubble     x_column, y_column, size_column, color_column, label_column,
             size_range, trend_line; series, point
  pie        label_column, value_column, format, sort, top, other_label;
             series, chart { hole, angle }, legend, label, value, percent
  stat       value_column (default: the first numeric column; first row),
             reduce, format (Python format), prefix, unit, label,
             thresholds, delta_mode, sparkline_length, value_columns;
             value { font-size }, delta, sparkline, unit, label
  text       column_list, separator, reverse, highlight; line, line-number,
             cell.null, chart { line-clamp }
  table      column_list, sort, row_thresholds; see above

A stat chart shows one value in large digits (one line when the window is
too narrow, or with `value { font-size: normal }`), its change since the
previous refresh (↑ 4.7%, ↓ 3.0%) and a sparkline of the last 20 refreshes;
the history starts when the dashboard starts. `delta` and `sparkline
{ display: none }` hide them. `reduce` picks the value of the rows (first,
last, mean, min, max, sum, count), `delta_mode: absolute` shows the change as
an amount, and `value_columns` shows several values side by side (names or
`{ column, label, format, unit, prefix }`).

A text chart shows the result as plain text, without a table: each row is
its cells joined by `separator` (default a space), so a one-column query
shows one line per row; strings are shown as they are, newlines in a cell
start new lines, NULL is `cell.null { content }` (default empty). Lines
wider than the window wrap at spaces (`line { word-break: break-all }`
anywhere, `white-space: nowrap` cuts them). `reverse` puts the last row
first and `highlight: [{ pattern, class }]` gives lines that match a Vim
regex a class (the first rule wins; default `warning`). The result must
still be rows (|dbdash-result|): turn a string from `lua://` or HTTP into
`{ { text = rs } }` with `query.transform` (|dbdash-transform|).

`axes.y_axis.format` takes a Python format such as "{:,.0f}", "{:.1%}" or
"{:.0f} ms" (text around the field is kept). `subtitle` is a muted line
under the title.

Line, area, scatter and bubble charts take Chart.js / ECharts options:
`series_column` turns long data (one row per x and series) into one series
per value; `span_gaps: false` breaks the line at NULLs; an axis takes
`scale: log` (one tick per power of ten) and `ticks` (about how many);
`mark_lines: [{ value, axis, label, class }]` draws reference lines at a
value or at the data's `mean`, `min` or `max` (on the x axis: a number or a
category; `mark.<class>` colors one); `mark_points: [max, min]` labels each
series' extremes; `trend_line: linear` adds a dashed least-squares line;
`stacked: percent` stacks areas to 100%; bubbles take `size_range: [min,
max]` (radius in canvas pixels). `example/charts/line.yaml` and the area,
scatter and bubble files show each option.

Bar charts draw several series (`y_columns` or `series_column`) side by side
or, with `stacked: true`, on top of each other (the value shown is the
total). `sort: asc | desc` orders them by value and `top` keeps the first N;
`axes.y_axis.min_value` / `max_value` set the value axis, and `mark_lines`
draw reference lines on it. Histograms take `bin_width` and `bin_range:
[from, to]` (values outside are left out), `cumulative` and `normalize:
percent | density`; their `mark_lines` are values of the data, and the bin
each falls in is colored (and labeled when horizontal). Box plots take
`whiskers` (iqr, the default; minmax; or two percentiles such as [5, 95]).
Heat maps take `scale_min` / `scale_max` (the range of the data the colors
span). Pie charts take `sort`, `top` (the rest in one slice named by
`other_label`, styled as `series.other`) and `format`.

Thresholds                                                 *dbdash-thresholds*

`show.thresholds` (stat), `thresholds` on a `column_list` entry (table) and
`show.row_thresholds.steps` (table rows) give values a class by steps; the
most severe step reached wins: >yaml
  thresholds:
    - { value: 100, class: warning }             # >= 100
    - { value: 500, class: danger, notify: true } # >= 500, and notify
  thresholds_below: false   # true: steps apply at or below (lower is worse)
<The class goes on the element (`value`, `cell`, `row`) and style sheets
color it: the default sheet colors `success`, `info`, `warning` and `danger`
(Bootstrap's contextual classes) with the Diagnostic groups; any other class
is yours to style (`value.critical { color: "#ff0000" }`; Grafana's color
modes are rules too: `value.danger { background-color: DiagnosticError }`).
With `notify: true`, the refresh where a value rises to that step notifies
once (vim.notify WARN, e.g. "Errors: 650 ≥ 500"); it notifies again after
falling back and crossing it again. For a table column the most severe cell
counts. Query failures are not thresholds: they show in the dashboard and
notify once.

Style sheets                                                      *dbdash-css*

All appearance is written in style sheets, as in a browser. A style sheet is
a mapping of selectors to properties: >yaml
  style:
    panel-title: { font-weight: bold }
    "#orders series": { color: "#61afef" }
    "row:nth-child(even)": { background-color: "#2c313a" }
    value.danger: { background-color: DiagnosticError }
<
A dashboard is a tree of elements (|dbdash-css-elements|), and every rule
whose selector matches an element applies to it. A chart's content is
elements too, one per item of the data, as an SVG chart or an HTML table
would be: a row and its cells, a line of text, a series, a bar, a legend
item. So rules can pick one item: `"row:last-child"`, `"cell:first-child"`,
`"legend-item:nth-child(2)"`, `"bar[category=Books] value"`. The screen
lines a long row wraps into, ticks and the canvas pixels are layout, not
elements.

Cascade                                                   *dbdash-css-cascade*

Style sheets come from five places, lowest first (CSS origins):

  1. the default sheet      how everything looks out of the box (UA)
  2. setup({ style })       yours, for every dashboard (user)
  3. `style` of a config    the dashboard's (author)
  4. `panels[].style`       one panel's; its rules match only inside it
                            (like an inline style, but with selectors)
  5. |:DbDashStyle|         changes made at run time

A later place wins over an earlier one. Within one place the more specific
selector wins (ids, then classes, attributes and pseudo-classes, then
element names, as in CSS), then the later rule. Inherited properties (color,
text-align, white-space, word-break, font-*, palette, renderer, canvas) pass
from an element to its children unless they set their own.

Selectors                                               *dbdash-css-selectors*

  panel              an element by name
  *                  any element
  #orders            the element with that id (a panel's `id`; panels
                     without one are numbered 1, 2, ...)
  .danger            an element with that class: the chart type of panels
                     and charts (`panel.line`, `chart.stat`), threshold
                     classes, `series.<name>`, `cell.null`, `delta.up`, ...
  [type=line]        an attribute (`chart[type=...]`, `series[name=...]`,
                     `cell[column=...]`, `header[column=...]`); [attr] for
                     any value
  :nth-child(even)   odd, even or N among elements of the same name;
                     :first-child, :last-child
  panel title        a descendant (any depth)
  chart::part(axis)  a part of an element (the same as `chart axis`)
  a, b               either

Colors are "#rrggbb", "#rgb", a name ("blue", "bright_blue") or a highlight
group ("DiagnosticOk"); a group alone keeps its own attributes and follows
the colorscheme.

Elements                                                 *dbdash-css-elements*

  dashboard          the grid container (|dbdash-layout|)
    header           the header line: header-title, description-icon,
                     countdown
    panel            a grid item; classes: its chart type; id: its `id`
      panel-title    the title line of a panel in a grid; subtitle
      description-icon, error, countdown
      args           the argument line: arg-name (.local for a panel's
                     own), arg-value
      chart          the chart; classes and [type]: its type
        title, subtitle   the chart's title (one-chart dashboards)
        plot         the plot area (border, height, min-height)
        axis, axis-title, label, grid (.x, .y), rule, note
        legend       > legend-item[name] (> label, value, percent: pie)
        series[name] one per series, slice or box, in order:
                     series:nth-child(N), series.<name>, series.other;
                     > point (lines, scatter: the markers), > value,
                     outlier, mean (box plots)
        mark[label]  one per mark_lines entry (.<class>)
        bar[category][series]  one per bar (.<category>) > value
        cell[x][y]   one per heat map cell
        stat         one per value (value_columns) > value (.<threshold
                     class>), unit, label, delta (.up, .down, .same),
                     sparkline
        table        > header[column] (one per column), row (one per
                     result row; .<row threshold class>) > cell[column]
                     (.null, .<threshold class>)
        lines        > line (one per result row; .<highlight class>);
                     line-number: the lines' numbers
  note, warning      notes ("… 3 more rows") and warnings

The sidebar is a document of its own: sidebar-dir, sidebar-item (.running,
.paused, .idle, .cursor).

Properties                                             *dbdash-css-properties*

Text:
  color, background-color       a color (color is inherited)
  font-weight                   normal, bold
  font-style                    normal, italic
  text-decoration               none, underline, undercurl, line-through
  text-align                    start, left, center, right
  vertical-align                top, middle, bottom (table cells)
  white-space                   normal (wrap), nowrap (one line)
  word-break                    normal, break-all (wrap anywhere)
  text-overflow                 ellipsis ("…"), clip, or a string
  line-clamp                    table: rows shown; text chart: lines shown
  font-size                     normal, big (stat value: block digits)

  display                       block, none (hides the element)
  content                       generated text: countdown format,

  border                        single, rounded, heavy, double, dashed,

  border-color                  a color
  padding                       N, [v, h], [top, h, bottom], [t, r, b, l]
  width, max-width              cell / bar width, the widest a chart gets
  height, min-height            plot rows, the most lines of a cell

  grid-template-areas, column-gap, row-gap, grid-area, grid-row,

Charts:
  renderer, canvas              how the chart is drawn (|dbdash-styles|)

The default sheet hides what is optional: countdowns, grid lines, point
markers on lines, the values of heat maps and box plots, box plot means,

animations and hover effects have no terminal equivalent.
`example/charts/css.yaml` shows the cascade and the common properties.

Rendering                                                 *dbdash-rendering*

A dashboard is drawn the way a browser draws a page (after Servo):

  DOM          the dashboard, its header, panels and charts as elements; a
               query result builds the chart's content elements (reusing
               them by position: a new result of the same shape only
               changes values); an error or a new argument value changes
               them; changes mark them dirty
  style        the cascade computes each element's style, restyling only
               what changed; elements alike for every selector share one
               computed style; each property says what a change of it costs:
               repaint (colors), relayout (sizes) or rebuild (renderer)
  layout       the grid places the panels; a chart is a replaced element,
               sized by layout and drawn by its renderer; a panel's layout
               is reused while nothing it depends on changed
  paint        the panels become layers of lines and highlights, with the
               rows of each element for hit testing
  composite    the layers become buffer lines; only the rows that changed
               are written
  events       a key is an event at the cursor: hit testing finds the
               element under it, the event goes from the root down to it
               and back up (capture and bubble), and the dashboard's keys
               are listeners on the root

Results, errors and push items only ask for a rendering update; all of them
until it runs become one update, at most one every 20 ms, and a hidden
dashboard renders when it is shown again. |:DbDashInspect| shows what the
style phase computed for the element under the cursor.

Renderers                                                      *dbdash-styles*

  type       renderer (first is the default)    canvas
  line       canvas, asciichart                 braille, quadrant, block,
  scatter    canvas                             halfblock, ascii
  area       canvas
  bubble     canvas
  bar        horizontal, vertical
  histogram  horizontal, vertical
  boxplot    boxdraw, vertical
  heatmap    halfblock, block
  pie        bar, circle                        (circle: canvas)
  table      box
  stat       big
  text       plain

Pick them with the `renderer` and `canvas` properties of the `chart`
element, for one panel, a dashboard or (setup) every dashboard: >lua

  require("dbdash").setup({
    style = {
      ["chart.line"] = { canvas = "quadrant" },
      ["chart.bar"] = { renderer = "vertical" },
    },
    ticks = "nice",           -- or "linear"
    register = {              -- your own implementations
      ["chart/bar/mine"] = require("my.bar_style"),
      ["canvas/sextant"] = require("my.sextant_canvas"),
    },
  })
<
A chart renderer is a table `{ render = fn }` where `fn(resultset, show,
ctx)` returns `{ lines, hl }`; `ctx.css` gives the computed style of the
chart's parts (`ctx.css:get("plot")`, `ctx.css:hl("series", { index = 1 })`).
A canvas has `new` and `px_per_char`, ticks `ticks` and `limits`, a palette
`color`, a frame `render`, `plot_size` and `apply_style`: one missing is an
error when it is registered. The interfaces are in
lua/dbdash/render/types.lua. Names in style sheets (`renderer`, `canvas`,
`palette`) are checked when a config loads.

The YAML parser supports a subset: block and flow collections, quoted and
plain scalars, block scalars, comments. Anchors, tags and multiple documents
are rejected with a line and column.

6. TEMPLATES                                                *dbdash-templates*

`query.sql` and `query.transform` are templates rendered before every run,
both the same way (the transform is never autoescaped); descriptions
(|dbdash-description|) are rendered the same way when shown. The language is
Jinja2 (3.1) with `trim_blocks` and `lstrip_blocks` enabled, undefined
values as errors (StrictUndefined) and the `loopcontrols` and `do`
extensions built in: statements, expressions, filters, tests and functions
behave as in Jinja2 (Python semantics), checked against Jinja2 itself.
dbdash adds SQL quoting, `args` / `meta` and Lua
(|dbdash-template-extensions|). The rendered text is what |:DbDashShowSQL|
(`s`) shows.

Variables                                              *dbdash-template-vars*

A template sees two names, the same in every template (query.sql,
query.transform, descriptions, imported templates) and in all Lua code
(|dbdash-lua|):

  args    the query arguments (|dbdash-arguments|): `args.min_age`
  meta    metadata about the dashboard (|dbdash-meta|): `meta.config_dir`

Argument values have these types:

  string          text
  number, int     a number
  boolean         true / false
  list            a list: `args.departments[0]`, `for d in args.departments`
  map             a mapping: `args.filters.region`, `args.filters.items()`
  no value        `none` (prints "None"; test with `is none`)

Any other name is an error ("'x' is undefined"), as in Jinja's
StrictUndefined; a bare argument name says how to write it ("'days' is
undefined; arguments are written args.days"). Test optional names with `is
defined`. `args` and `meta` themselves cannot be assigned: not as `set` or
`for` targets, macro names or parameters, or `import ... as` names. One
argument can (|dbdash-assign-args|).

Assigning arguments                                     *dbdash-assign-args*

`{% set args.days = 30 %}` in a template, or `args.days = 30` in any Lua of
the panel (`{% lua %}`, imported `.lua`, `query.transform`, `lua://`; not in
descriptions, where it is an error), sets an argument:

- the rest of the run sees it: later template text (macros and imported
  templates too), `query.transform`, `lua://` (in Lua, the same code sees
  `args` change at once, the rest of the run once that code returns: a
  block, a module function, the script);
- it is kept like an edit in the dashboard (`a`): shown by `A` and the
  `args_show` line, used from the next refresh on, saved in sessions, and
  reset by `R`; the config file is not changed;
- the name must be an argument the panel sees (a panel's own argument
  shadows a shared one, which other panels see from their next refresh)
  and the value must fit its `type` (none / nil clears it);
- in a `dbdash.run()` callback (|dbdash-callback|) it changes that run and
  is kept too; the run that called it keeps its own values.

`{% set args = ... %}`, `{% set args['x'] = ... %}` and `{% set meta.x %}`
are errors.

Three tables hold arguments: the dashboard's values (`a`, the command line,
sessions, defaults), a copy of them for each refresh (`args` in its code),
and for a callback a new table: the caller's `args` with the table given to
`dbdash.run()` over them (that table itself is only read). An assignment
changes the `args` of the run it is in, and the dashboard's values when that
code returns. With `days` 0 and a callback that assigns 10: >lua
  local copy = vim.deepcopy(args)  -- copy.days = 0
  copy.days = 14                   -- args.days is still 0
  local r = dbdash.run(copy)       -- the callback runs `args.days = 10`
<
  - the callback starts with `days` 14 (from `copy`); after its assignment,
    the rest of the callback sees 10: its query uses 10 when the assignment
    comes before `{{ args.days }}` in `query.sql`, but 14 when it is made in
    its `query.transform` (the query already ran);
  - the dashboard's `days` becomes 10 when the callback's code returns;
  - the caller's `args.days` stays 0 for the rest of this refresh, and
    `copy.days` stays 14;
  - the next refresh starts with 10 (`R` goes back to 0).

When the caller assigns the same argument too, the last one to be applied
wins: the caller's, applied when its own code returns (after the callback).
So with `local copy = args` (the same table, no copy), `copy.days = 14`
assigns the caller's `days`, and the next refresh starts with 14, not 10.

More cases:
  - a callback that does not assign keeps nothing: the values given to
    `dbdash.run()` are only that run's;
  - the caller assigns, then calls `dbdash.run()` in the same code: the
    callback starts from the caller's new value (unless given another);
  - two callbacks in one refresh: each starts from the caller's values, not
    from what the other one assigned;
  - nested callbacks: each level has its own table; when the innermost one
    assigns, the levels above keep their values and the dashboard gets the
    innermost value (unless a level above assigns it later);
  - an assignment is applied when its code returns: when that code fails it
    is not applied, but one applied before a later failure in the refresh
    is kept;
  - assigning the value the run already has changes nothing.

Metadata                                                        *dbdash-meta*

`meta.<name>` holds read-only values computed for each render (none / nil when
there is no value; in Lua `meta.run` and `meta.runs` follow the run as it
goes, |dbdash-runs|):

  cwd            Neovim's current directory
  config_file    the config file (absolute path)
  config_dir     its directory
  config_name    its name without the extension
  dashboard_title  the top-level `title`
  db_type        the panel's database type (postgres, http, lua, ...): its
                 own `database`, else the top-level one (|dbdash-panels|)
  db_host        host, port, database (SQLite file, HTTP path) and user of the
  db_port        URL as written in the config, with the driver's default port
  db_name
  db_user
  db_url         the URL as written, password masked, ${NAME} not expanded
  panel_index    the panel's number (from 1)
  panel_title    `show.title`
  chart_type     `show.type`
  interval       the refresh interval in ms
  max_rows       `query.max_rows`
  timeout        the query timeout in ms
  refresh_count  how many times this panel has refreshed (from 1)
  run            this run's record (|dbdash-runs|): `run.kind` is "refresh"
                 or "callback", `run.depth` 0 in a refresh, n in a
                 dbdash.run() callback n levels deep (|dbdash-callback|)
  runs           the records of this refresh's life so far: the refresh,
                 then its callbacks in the order they started
  prev           the previous refresh's record (succeeded or failed):
                 `prev.error` when it failed
  prev_ok        the last successful refresh's record: its query result
                 before `query.transform` in `prev_ok.query` and its rows
                 in `prev_ok.result`
  prev_runs      the records of the previous refresh's life
  prev_ok_runs   the records of the last successful refresh's life
  now            render time, ISO 8601 with the UTC offset
                 (2026-11-24T10:00:00+08:00)
  today          the date (2026-11-24)
  hostname       this machine's name
  user           the operating system user
  nvim_version   e.g. 0.12.0
  os             linux, windows, macos or bsd
  arch           x64, arm64, ...

No password and no expanded environment variable is part of the metadata.
In the dashboard's description (|dbdash-description|) the panel fields
(`panel_*`, `chart_type`, `interval`, `max_rows`, `timeout`,
`refresh_count`, `run`, `runs`, `prev`, `prev_ok`, `prev_runs`,
`prev_ok_runs`) are none and `db_*` describe the top-level database.

Run records                                                     *dbdash-runs*

Every run of a panel's pipeline (a refresh, or a `dbdash.run()` callback,
|dbdash-callback|) has a record. A refresh and the callbacks it makes are one
life, from that refresh until the next one starts. A record has:

  id           a UUID version 7 (made in Lua; within one Neovim ids are
               unique and increase)
  kind         "refresh", "callback" or "push" (an item of a push source,
               |dbdash-push|)
  depth        0 for a refresh, n for a callback n levels deep
  parent_id    the id of the run that called it (none for a refresh)
  refresh_id   the id of the refresh of its life (its own for a refresh)
  args         the arguments it started with (a callback: merged)
  started_at   when it started, milliseconds since the Unix epoch
  finished_at  when it ended (none while it runs)
  elapsed_ms   finished_at - started_at (none while it runs)
  ok           true or false (none while it runs)
  error        its error when it failed, as the dashboard shows it
  sql          the rendered `query.sql`
  query        the query's result before `query.transform`: { columns,
               types, rows }, or the raw value of `lua://` / `http(s)://`
  result       the final rows: { columns, types, rows } (what
               `dbdash.run()` returns)

What a failed run got before it failed is kept (a query that worked keeps
`query` when its transform fails). `meta.runs` holds the life so far: in
Lua it is live (after `dbdash.run()` returns, the callback's finished record
is in it); templates see `meta.run` and `meta.runs` as they were after the
last Lua code that ran ({% lua %} blocks, module functions). >lua
  for _, r in ipairs(meta.prev_runs or {}) do
    print(r.kind, r.depth, r.id, r.parent_id, r.elapsed_ms, r.ok)
  end
<
`:DbDashShowSQL` and descriptions are not runs: their `meta.run` has kind
"render" and they leave `runs` and `prev*` alone. The records of up to
three lives are kept (this one, `prev_runs` and `prev_ok_runs`), with their
data, so a refresh with many callbacks and large results holds that much
memory.

Syntax                                                *dbdash-template-syntax*

  {{ expr }}          output an expression
  {% stmt %}          statement
  {# ... #}           comment
  {%- / -%}  {{- / -}}  strip whitespace before / after the tag
  {%+                 keep the indentation that lstrip_blocks would remove

With `trim_blocks` the newline after a statement tag is removed, and with
`lstrip_blocks` spaces before a statement tag at the start of a line are
removed, so statements on their own lines leave no blank lines: >jinja
  SELECT * FROM users
  WHERE 1 = 1
  {% if args.min_age %}
    AND age >= {{ args.min_age }}
  {% endif %}
<
Statements:

  {% if a %} ... {% elif b %} ... {% else %} ... {% endif %}
  {% for x in xs %} ... {% else %} (empty) ... {% endfor %}
  {% for k, v in m.items() if v %} ... {% endfor %}   (only items with v)
  {% for x in tree recursive %} ... {{ loop(x.children) }} ... {% endfor %}
  {% break %}  {% continue %}  {% do expr %}
  {% set name = expr %}       {% set a, b = 1, 2 %}
  {% set name %} ... {% endset %}        the output; {% set n | upper %} too
  {% set args.name = expr %}  assign an argument (|dbdash-assign-args|)
  {% with a = 1, b = 2 %} ... {% endwith %}
  {% filter upper | replace('A', 'B') %} ... {% endfilter %}
  {% raw %} {{ not rendered }} {% endraw %}
  {% macro name(a, b=default) %} ... {% endmacro %}
  {% call(x) name(args) %} ... {% endcall %}   the macro's caller(x)
  {% import 'file.sql' as lib %}         then {{ lib.name(...) }}
  {% from 'file.sql' import name, other as alias %}
  {% include 'file.sql' %}               |dbdash-template-imports|
  {% extends 'base.sql' %}  {% block name %} ... {% endblock %}
  {% autoescape false %} ... {% endautoescape %}
  {% import 'file.lua' as h %}           a Lua module, |dbdash-template-lua|
  {% lua %} ... {% endlua %}             Lua code, |dbdash-template-lua|

Inside a loop: `loop.index` (from 1), `loop.index0`, `loop.revindex`,
`loop.revindex0`, `loop.first`, `loop.last`, `loop.length`, `loop.depth`,
`loop.depth0`, `loop.previtem`, `loop.nextitem`, `loop.cycle(a, b, ...)`,
`loop.changed(value)`. A `set` inside a loop, `with`, macro or block does not
change the variable outside it (Jinja scoping).

A macro whose body uses `varargs`, `kwargs` or `caller` takes extra positional
arguments, extra keyword arguments or a call block. Calls take `*list` and
`**mapping` as in Python: `{{ m(*xs, **opts) }}`.

Expressions:

  literals     'text' "text" 42 0x1f 0o17 0b101 1_000 3.14 1e3 true false
               none (True/False/None too) [1, 2] (1, 2) {'key': value}
  access       m.key  m['key']  xs[0]  xs[-1]  'text'[1]
  slices       xs[1:]  xs[:-1]  'text'[::-1]  xs[a:b:step]
  math         + - * / // % **      (/ always divides, // floors)
  strings      'a' ~ b (concatenate as text)   'a' + 'b'
  compare      == != < <= > >=   x in xs   x not in xs
  logic        and or not        a if cond else b
  tests        x is defined, x is not none, ...
  filters      x | name   x | name(arg, key=value)   chained left to right
  calls        macro(...)  range(...)  and the methods below

Truthiness follows Python: none, false, 0, "" and empty lists and mappings
are false.

Filters                                              *dbdash-template-filters*

All of Jinja's built-in filters, with Jinja's arguments:

  default(value, boolean=false)  (alias d) value when x is undefined; with
                         boolean=true also when x is false/empty/none
  length                 (alias count) items of a list, mapping or string
  upper, lower, capitalize, title   change case
  trim(chars)            strip whitespace (or the given characters)
  replace(old, new, count)
  join(sep, attribute=)  join items; attribute picks a key of each mapping
  first, last            first / last item
  int(default=0, base=10)  to integer ("ff"|int(base=16) is 255)
  float(default=0.0)     to float
  string                 to text
  abs                    absolute value
  round(precision=0, method='common')  'common' rounds half to even like
                         Python, 'ceil' and 'floor' round up or down
  tojson(indent)         JSON text (use it to put values into MongoDB queries)
  safe                   mark as SQL so autoescape leaves it alone
  escape (alias e), forceescape   in SQL templates the database's literal
                         (what autoescape writes), elsewhere HTML escaping
  format(*args, **kw)    printf-style: '%s=%d'|format(name, n)
  center(width=80), indent(width=4, first=false, blank=false),
  truncate(length=255, killwords=false, end='...', leeway=5),
  wordwrap(width=79, break_long_words=true, wrapstring, break_on_hyphens),
  wordcount, striptags, filesizeformat(binary=false), pprint, urlencode,
  urlize(trim_url_limit, nofollow, target, rel, extra_schemes),
  xmlattr(autospace=true)   text helpers as in Jinja; in SQL templates the
                         output of urlize and xmlattr is still autoescaped
  list, items, reverse, unique(case_sensitive, attribute),
  sort(reverse=false, case_sensitive=false, attribute=),
  dictsort(case_sensitive=false, by='key', reverse=false),
  min, max (case_sensitive, attribute), sum(attribute, start=0),
  batch(count, fill_with), slice(count, fill_with), random,
  groupby(attribute, default, case_sensitive)   rows by a key: (grouper, list)
  map('filter', ...), map(attribute='x', default=)
  select('test', ...), reject('test', ...), selectattr('x', 'test', ...),
  rejectattr('x', 'test', ...)   keep or drop items by a test
  attr(name)             an attribute (not a mapping's key)

Filters that give a generator in Jinja (map, select, reverse, ...) give a
list here, so `{{ xs|map('upper') }}` prints the list.

SQL filters, quoted for the panel's database (|dbdash-template-dialects|):

  sql_quote              a literal: 'it''s', 42, TRUE, NULL
  sql_escape             string content without the quotes: it''s
  sql_in                 a list as (1, 2, 3); a mapping uses its keys;
                         an empty list gives (NULL), so `x IN (NULL)`
                         matches nothing
  sql_id                 an identifier: "order", "public"."t" (dots split
                         the parts)
  sql_limit              a positive integer, or "" for none; anything else
                         is an error

For curl commands (|dbdash-http|), whatever the database:

  shell_quote            one shell word: 'it'\''s', none as ''; a list
                         gives one word per item

Functions:

  range(stop) range(start, stop[, step])   integers, like Python
  dict(a=1, ...)         a mapping
  namespace(a=1, ...)    an object whose attributes `{% set ns.a = v %}`
                         changes from inside loops (where `set` is local)
  cycler(a, b, ...)      .next() gives a, b, a, ...; .current, .reset()
  joiner(sep=', ')       a function giving "" the first time, then sep
  lipsum(n=5, html=true, min=20, max=100)   lorem ipsum paragraphs
  sql_case(conditions, default)  CASE WHEN <key> THEN <value> ... ELSE
                         <default> END from a mapping; keys and values are
                         inserted as written
  sql_concat(a, b, ...)  CONCAT(...) (SQLite: a || b); strings become quoted
                         literals, other values are inserted as text

Tests (`x is name`, `x is not name`, `x is name(arg)`): defined, undefined,
none, boolean, true, false, number, integer, float, string, mapping,
sequence, iterable, callable, escaped, lower, upper, odd, even,
divisibleby(n), sameas(x), in(seq), filter, test, and the comparisons eq
(== equalto), ne (!=), gt (> greaterthan), ge (>=), lt (< lessthan),
le (<=), which select('>', 3) also takes.

Methods, as in Python (`'a,b'.split(',')`, `'{:.2f}'.format(x)`):

  strings      capitalize() casefold() center() count() endswith()
               expandtabs() find() format() format_map() index() isalnum()
               isalpha() isascii() isdecimal() isdigit() isidentifier()
               islower() isnumeric() isspace() istitle() isupper() join()
               ljust() lower() lstrip() partition() removeprefix()
               removesuffix() replace() rfind() rindex() rjust()
               rpartition() rsplit() rstrip() split() splitlines()
               startswith() strip() swapcase() title() upper() zfill()
  mappings     items() keys() values() get() copy() update() pop()
               popitem() setdefault() clear()
  lists        index() count() copy() append() extend() insert() pop()
               remove() reverse() sort() clear()
  tuples       index() count()

Methods that change a value cannot change `args` or `meta` (they are
read-only; |dbdash-assign-args| sets an argument). Strings also format with
`%`: `'%s: %.1f' % (name, value)`.

Examples: >jinja
  WHERE status = {{ args.status | sql_quote }}
    AND dept IN {{ args.departments | sql_in }}
    {% if args.search is not none and args.search | trim %}
    AND name LIKE {{ ('%' ~ args.search ~ '%') | sql_quote }}
    {% endif %}
  ORDER BY {{ args.sort_column | sql_id }}
  LIMIT {{ args.limit | sql_limit }}
<
Autoescape                                        *dbdash-template-autoescape*

With `query.autoescape: true`, every `{{ value }}` is written as a literal of
the database's dialect, as if `| sql_quote` were applied: strings are quoted
and escaped, lists become (a, b), none becomes NULL, numbers and booleans
stay literals. In the curl command of an `http(s)://` query a value becomes
a shell word instead, as if `| shell_quote` were applied (|dbdash-http|).
Output of the SQL filters and functions and of `| safe` is inserted as is,
so use `| safe` for SQL fragments such as column names: >jinja
  SELECT {{ args.column | safe }} FROM t WHERE name = {{ args.name }}
<A mapping cannot be autoescaped (use `| tojson` or pick a key). Values
inside `{% %}` statements are never escaped.

Dialects                                            *dbdash-template-dialects*

The SQL filters and autoescape follow the database type:

  sqlite, postgres, cassandra   'it''s'  "ident"  TRUE/FALSE
  mysql                         'it\'s'-style backslash escapes, `ident`
  mssql                         N'...' for non-ASCII text, [ident], 1/0
  mongodb                       JSON: "text", [1, 2], {"k": 1}, true, null
  redis                         "double quoted" with backslash escapes, 1/0
  http                          shell words for curl: 'it'\''s', a list
                                as one word per item, none as ''

Imports                                              *dbdash-template-imports*

Paths in import, from-import, include and extends are relative to the config
file's directory.

`{% include 'part.sql' %}` writes another template's output where it stands;
it sees the template's variables (`without context`: only `args` and
`meta`). `ignore missing` skips a file that does not exist, and a list of
names uses the first that does. `{% extends 'base.sql' %}` renders base.sql
with this template's blocks instead: a block replaces the block of the same
name there, `{{ super() }}` writes the replaced block and `{{ self.name() }}`
writes a block again; `scoped` blocks see the loop around them, `required`
blocks must be given by the extending template.

An imported file exports its macros and top-level variables
(`set`; names starting with "_" stay private). It always sees `args` and
`meta`; the importing template's own variables (`set`, `for`) only with
`with context` (`{% import 'x.sql' as x with context %}`), otherwise pass
them as macro arguments: >jinja
  {# macros/filters.sql #}
  {% macro in_list(column, values) -%}
  {{ column | safe }} IN {{ values | sql_in }}
  {%- endmacro %}

  {# query.sql #}
  {% from 'macros/filters.sql' import in_list %}
  SELECT * FROM users WHERE {{ in_list('dept', args.departments) }}
<
Lua in templates                                         *dbdash-template-lua*

Templates can run Lua, the same way in query.sql, query.transform and
imported templates:
>yaml
  query:
    sql: |
      {% import 'lua/helpers.lua' as h %}
      SELECT * FROM visits
      WHERE day >= {{ h.since(args.days) }}
      {% lua %}
        if meta.os == "windows" then return "AND host = 'win'" end
      {% endlua %}
<
`{% lua %} ... {% endlua %}` runs the Lua code where it stands and outputs
what it returns, like `{{ }}` (autoescape applies; nil outputs nothing). The
code is taken as written: `{{` and `{%` inside it are Lua.

`{% import 'x.lua' as h %}` and `{% from 'x.lua' import f %}` load a Lua
file that returns a table (paths as for template imports). Its functions are
called from expressions, `{{ h.f(args.days) }}`, with positional arguments
only; other values are exported as they are. A module runs once per render,
so its functions see that render's `args` and `meta`. In a `{% lua %}` block,
`vars.h` is the module's own table.

Lua code sees the globals (`vim`, `os`, ...) plus:

  args         the dashboard arguments (|dbdash-arguments|); assigning one
               sets it (|dbdash-assign-args|)
  meta         the metadata (|dbdash-meta|), read-only
  store        the panel's own table, kept while the dashboard runs
               (|dbdash-store|)
  vars         ({% lua %} blocks) the template variables visible there:
               `set`, `for` and macro arguments, read-only
  dbdash.*     the helpers of |dbdash-lua| (system, query, sleep, ...) and
               `dbdash.safe(s)`: output s as is, even with autoescape

Values cross over as: none -> nil, lists -> Lua lists, mappings -> tables (in
`vars`, undefined names are nil too; passing an undefined value to a module
function is an error); back: nil -> none, Lua lists -> lists, other tables ->
mappings (keys sorted). The code runs while the dashboard refreshes, without
blocking the editor (the dbdash.* helpers wait), and is stopped at the query
timeout. Errors name the file and line: the config's line for a block, the
.lua file's for a module.

A config with Lua in its templates or imports is trusted before it runs,
together with the files it imports, includes or extends (|dbdash-lua|).

Extensions and differences                    *dbdash-template-extensions*

What dbdash adds to Jinja2, or does differently:

- `args` and `meta` are global variables: every template sees them,
  including imported and included ones (with or without context). They
  are read-only: methods that change a value (`append`, `update`, ...)
  refuse them, and `{% set meta.x %}` is an error.
- `{% set args.name = value %}` sets an argument (|dbdash-assign-args|).
- `{% lua %} ... {% endlua %}` and importing `.lua` modules
  (|dbdash-template-lua|).
- The SQL filters and functions (`sql_quote`, `sql_in`, ..., `sql_case`,
  `sql_concat`) and `query.autoescape`, which writes literals of the
  database (|dbdash-template-autoescape|). In SQL templates `escape`, `e`
  and `forceescape` write such literals too (not HTML), and the output of
  `urlize` and `xmlattr` is still autoescaped. Elsewhere (descriptions)
  autoescape and `escape` are HTML escaping, as in Jinja2.
- Filters that return a generator in Jinja2 (`map`, `select`, `reverse`,
  ...) return a list.
- Numbers from the database and from Lua are ints when they have no
  fraction (Lua has one number type).
- Custom filters and tests cannot be added.

Errors                                                *dbdash-template-errors*

Syntax and runtime errors stop the refresh and are shown in the dashboard
with the file and line: the config's for query.sql, query.transform and
descriptions (a description's error is notified when it is shown), e.g.
"board.yaml:12: 'region' is undefined", the imported file's own for an error
in an imported template or `.lua` module. A bare argument name says how to
write it: "'days' is undefined; arguments are written args.days".

Numbers are ints and floats as in Python: `{{ 4 / 2 }}` is `2.0`. Numbers
from the database and from Lua are ints when they have no fraction.

7. ARGUMENTS                                                *dbdash-arguments*

Arguments are the variables of the query template, written `args.<name>` in
templates and Lua code. The top-level `args` are shared: every panel can use
them. A panel's `query.args` are its own: only that panel sees them, and one
with the name of a shared argument shadows it there. A one-chart config
follows the same rule (its `query.args` win over top-level `args`). >yaml
  args:
    - name: departments     # used as args.departments (letters, digits, _)
      type: list            # string (default) | number | int | boolean |
                            # list | map
      default: [IT, HR]     # value when nothing else sets it
      required: false       # ask at start when there is no value
      show: true            # include in the args_show line
      choices: [IT, HR, Finance]   # completion and picker candidates
      description: "Departments to include"
<
An argument without a default and without a value is `none` in templates
(|dbdash-template-vars|). An argument is named with `name:` (`key:` is
rejected).

A local argument has its own value, set as `<panel>.name`, where `<panel>`
is the panel's `id` (default its number): >vim
  :DbDashStart board.yaml region=EU orders.region=US limit=5
<
`name=value` sets every argument of that name (the shared one and each
panel's own); `<panel>.name=value` only that panel's and wins over `name=`.
A panel's own argument whose name no other argument has is also just
`name`: the argument list (`A`), the editor (`a`) and saved sessions write
`<panel>.name` only for names that clash.

Where values come from (highest first):

  1. the command line: `:DbDashStart board.yaml min_age=30 ids=1,2,3`
  2. edits in the dashboard: `a` / |:DbDashModifyVariable|,
     |:DbDashUpdateVariable|, and assignments from templates and Lua
     (|dbdash-assign-args|)
  3. interactive input at start: `required` arguments without a value, or
     every argument with `:DbDashStart!`
  4. `default`

Values last until the dashboard stops (|:DbDashStop|, or closing its last
window); `R` / |:DbDashResetVariables| goes back to the defaults. Changing a
value in the dashboard refreshes it (all panels); an assignment from a
template or Lua does not (it applies from the next refresh).

Text input (command line, prompts) is parsed by type:

  string   as written
  number   a number; int: an integer
  boolean  true/false, 1/0, yes/no (any case)
  list     a,b,c   (empty input: empty list)
  map      key:value,key2:value2

List items and map values are numbers when the `default` and `choices` are
all numbers, strings otherwise. Escape `,` and `:` with a backslash, or quote
the item: `names='Smith, J',"a:b"`. On the command line, write a space in a
value as `\ `: `title=two\ words`.

`show.args_show: true` shows argument values above the chart (in a grid,
under the panel's title): the arguments its query reads (`query.sql`,
`query.transform` and what they import, found by name; all of them when the
code uses `args` as a whole) and its own `query.args`, except those with
`show: false`. A list of names shows those instead: `args_show: [region]`.
Local arguments are highlighted with `DbDashArgLocal`. The top-level
`show.args_show` is the default of every panel. `A` /
|:DbDashShowVariables| lists all arguments with their values (and the
default when the value differs).

8. DATABASES                                                *dbdash-databases*

URL: `<scheme>://[user[:password]@]host[:port][/database][?param=value]`

  sqlite:///absolute/path.db   sqlite://relative/to/config.db
  sqlite:///:memory:

Schemes also accepted: `sqlite3`, `postgresql`, `mariadb`, `rediss` (Redis
with TLS), `mongodb+srv`, `cql`, `sqlserver`. `lua://` runs Lua
(|dbdash-lua|) and `http://` / `https://` call an HTTP API (|dbdash-http|).
`luastream://`, `exec://` and `webhook://` are push sources: their data
arrives instead of being queried (|dbdash-push|). `database.type` is inferred
from the scheme.

Common parameters: `tls` (disable | require | pin | verify-ca |
verify-full), `fingerprint` (sha256:AB:CD:..., required for pin), `ca`
(CA bundle for verify-*, relative to the config file), `tls_host` (name to
verify instead of the URL host), `connect_timeout` and `timeout` (default
10s and 30s, see `defaults` in |dbdash-setup|), `application_name`.

SQLite options (`database.options`): `lib_path`, `readonly`, `create`
(create a missing file; off by default). On Windows put sqlite3.dll (from
https://sqlite.org/download.html) next to nvim.exe or on PATH, or point
`lib_path` at it; winsqlite3.dll of newer Windows versions is used
otherwise. `sqlite:///C:/data/app.db` is a drive path there.

Cancelling queries                                           *dbdash-cancel*

A running query is cancelled when the dashboard stops (|:DbDashStop|,
closing its last window, deleting its buffer, quitting Neovim), when a new
refresh replaces it (|:DbDashRestart|, `r`, changed or reset arguments) and
when its time is up (`connect_timeout` + `timeout`). Timer refreshes do not
cancel: they are skipped while a query runs.

Cancelling always goes the same way: dbdash stops waiting at once (the
result is dropped), then stops the query on the server, then closes the
connection. The callbacks of the refresh (|dbdash-callback|) and its Lua
code are cancelled with it. On the server:

  PostgreSQL   a CancelRequest on a new connection
  MySQL        KILL QUERY on a new connection (a user can kill the
               queries of its own connections)
  SQL Server   an attention packet on the query's connection
  MongoDB      killOp of the operation, found by its comment with
               $currentOp (servers 4.4 and newer; users can kill their own
               operations; `operation: command` is only disconnected)
  SQLite       the query is interrupted
  lua://       the script stops (|dbdash-lua|)
  Redis, Cassandra, HTTP   nothing: the connection is closed

A cancelled refresh is not an error: the panel keeps its result, its run
record (|dbdash-runs|) has `ok = false` and the error "query cancelled:
<reason>", and |:DbDashStatus| lists it as cancelled. When Neovim quits it
waits up to a second for the cancels to reach the servers.

Passwords                                                 *dbdash-passwords*

Passwords do not have to be written in config files. A password in the URL
wins, then `database.password_cmd`, then `passwords.json`:

- `${NAME}` anywhere in `database.url` is replaced by the environment
  variable NAME (URL characters in the value are percent-encoded; `$${`
  writes a literal `${`): `postgres://app:${APP_DB_PASSWORD}@db/app`.
  An unset variable is reported with the line of the URL.
- `database.password_cmd` runs a command when the URL has no password and
  uses the first line it prints. A string runs through `sh -c` (`cmd /c` on
  Windows), a list runs directly: >yaml
    database:
      url: "postgres://app@db.internal:5432/app"
      password_cmd: "pass show db/app"     # or [pass, show, db/app]
<  It runs in Neovim's current directory. The output is cached until Neovim
  exits or the server rejects it.
- `stdpath("data")/dbdash/passwords.json` (e.g.
  ~/.local/share/nvim/dbdash/passwords.json) maps URLs without passwords to
  passwords, most specific first: `scheme://user@host:port/db`, then
  `scheme://user@host:port`, then `scheme://user@host` (ports filled in with
  the database's default): >json
    { "postgres://app@db.internal:5432/app": "secret",
      "redis://cache.internal:6379": "redis-secret" }
<  Keep it readable by you only (chmod 600; `:checkhealth dbdash` warns
  otherwise). Changes are picked up without restarting.

PostgreSQL  `postgres://user:pass@host:5432/db`  cleartext, md5 and
            SCRAM-SHA-256 authentication; `options` URL parameter is sent as
            the startup `options`.
MySQL       `mysql://user:pass@host:3306/db`  mysql_native_password and
            caching_sha2_password (without TLS the password is sent
            RSA-encrypted with the server's public key).
Redis       `redis://[user]:pass@host:6379/0`  the query is one command,
            e.g. `HGETALL "user:1001"`; replies become tables (GET: key,value;
            HGETALL: field,value; ZRANGE ... WITHSCORES: member,score; INFO:
            section,key,value; SCAN iterates the cursor; others: value,
            index,value or key,value).

MongoDB     `mongodb://user:pass@host:27017/db?authSource=admin`
            SCRAM-SHA-256 (or `authMechanism=SCRAM-SHA-1`). The query is a
            JSON document: >json
              {"collection": "orders", "operation": "find",
               "filter": {"status": "paid"}, "projection": {"_id": 0},
               "sort": {"created_at": -1}, "limit": 100, "flatten": 1}
<           operation: find | aggregate (`pipeline`; omit `collection` for
            database-level stages such as $documents) | count | distinct
            (`field`) | command (`"command": {...}`, the reply as one
            row). Use Extended JSON for special values ({"$oid": ...},
            {"$date": "2026-01-01T00:00:00Z"}, {"$numberLong": "1"}) and
            `| tojson` in templates. Columns are the union of top-level keys;
            `flatten` expands nested documents to a.b columns.
            Seed lists (`mongodb://h1:27017,h2:27017/db`) are tried in order;
            the driver follows hello's `primary` to the writable member, or
            with `readPreference=secondary|secondaryPreferred|nearest|
            primaryPreferred` uses the first reachable member.
            `mongodb+srv://cluster.example.net/db` resolves the
            `_mongodb._tcp` SRV records (targets must be in the same domain)
            and the TXT options `authSource`, `replicaSet`, and defaults to
            `tls=verify-full`. Name servers come from /etc/resolv.conf (or
            DnsQuery on Windows); `dns=host:port` picks one.
Cassandra   `cassandra://user:pass@host:9042/keyspace?consistency=LOCAL_ONE`
            CQL with paging; PasswordAuthenticator.
SQL Server  `mssql://user:pass@host:1433/db`  SQL authentication. With
            `tls=require|pin|verify-*` the connection is encrypted with TLS
            negotiated inside TDS (TLS 1.2); `&encrypt=strict` uses TDS 8
            (SQL Server 2022+: TLS first, may be TLS 1.3). SQL Server sends
            only its leaf certificate, so `ca=` should include intermediates.

Lua         `lua://`  the query is Lua code, see |dbdash-lua|.
HTTP        `https://api.example.com/v1` (or `http://`)  the query is a
            curl command whose URL is a path under it, see |dbdash-http|.

Each refresh opens a connection, runs the query and closes it.

Result format                                                 *dbdash-result*

Every query, of any database, ends with a check that its result is rows
(after `query.transform`, |dbdash-transform|). SQL databases, Redis, MongoDB
and Cassandra return rows already. A `lua://` script, an HTTP response (its
decoded JSON) and a transform must have one of these shapes, written here
in Lua (in JSON: arrays and objects): >lua
  -- columns and rows by position
  { columns = { "a", "b" }, rows = { { 1, "x" }, { 2, "y" } } }
  -- columns and rows by name
  { columns = { "a", "b" }, rows = { { a = 1, b = "x" } } }
  -- records: a list of objects; columns sorted by name,
  -- or in the order of a `columns` list next to them
  { { a = 1, b = "x" }, { a = 2, b = "y" } }
<Without `columns`, rows by position get the names c1, c2, ... A missing
value, nil, `dbdash.null` or JSON null is NULL. Each column's type follows
its first non-NULL value: integer, number, boolean, string, or json for a
table (shown as JSON). `query.max_rows` keeps the first rows.

Anything else is an error with what was found, e.g. "the result is not rows
(got string)" or "the result is an object (data, total), not rows"; for a
query without a transform it adds "add query.transform to reshape it". So
in JSON `[{"a": 1}]` and `{"columns": ["a"], "rows": [[1]]}` show directly,
while `{"data": [...]}`, a number or text need a transform, e.g.
`return rs.data` or `return { { text = rs } }`.

Lua queries and transforms                                        *dbdash-lua*

A `lua://` database runs `query.sql` as Lua, and `query.transform` reshapes
the result of any database (including `lua://`) with Lua. Templates can run
Lua too (|dbdash-template-lua|): >yaml
  database: { url: "lua://" }
  query:
    args: [{ name: days, type: int, default: 7 }]
    sql: |
      local rows = {}
      for i = 1, args.days do
        rows[i] = { os.date("%m-%d", os.time() - i * 86400), i * i }
      end
      return { columns = { "day", "n" }, rows = rows }

  # any database:
  query:
    sql: SELECT day, amount FROM sales
    transform: |
      local out = {}
      for _, r in ipairs(rs.rows) do out[#out + 1] = { r[1], r[2] / 100 } end
      return { columns = { "day", "amount_usd" }, rows = out }
<
Both go through the template like SQL (|dbdash-templates|; values are
inserted as written, and `transform` never autoescapes), so reading the
arguments from `args` is usually simpler. They run inside the
refresh without blocking the editor and see the globals (`vim`, `io`, ...)
plus:

  args                  the dashboard arguments by name (`args.days`);
                        assigning one sets it (|dbdash-assign-args|)
  meta                  the metadata (`meta.config_dir`, |dbdash-meta|),
                        read-only
  store                 the panel's own table, kept while the dashboard
                        runs (|dbdash-store|)
  rs, response          (transform) the query result, see
                        |dbdash-transform|
  dbdash.system(cmd, opts)  run a command (a string through `sh -c` or
                        `cmd /c`, or a list) and wait without blocking;
                        returns { code, stdout, stderr }
  dbdash.query(url, query, opts)  run a query on any database; returns a
                        result set (`columns` with `name`, `rows`); with
                        `opts.raw = true` a `lua://` or `http(s)://` query
                        returns its raw value and the HTTP response
  dbdash.sleep(ms)      wait without blocking
  dbdash.checkpoint()   let the editor run during a long computation
  dbdash.run(args)      run this panel's query again with other arguments
                        and return its rows (|dbdash-callback|)
  dbdash.null           NULL in returned rows (nil works too)
  dbdash.safe(s)        (templates) output s as is, even with autoescape

example/lua_globals.lua declares these names for lua-language-server: add its
directory to `workspace.library` to get completion and checks in your configs'
Lua.

                                                                *dbdash-store*
`store` is a table each panel keeps for as long as its dashboard runs: every
Lua of the panel sees the same one (`{% lua %}` blocks, imported `.lua`
modules, `query.transform`, `lua://`, its description), and it survives
refreshes and argument changes. Panels do not share it, and it starts empty
when the dashboard is started again (it is not saved in sessions): >lua
  store.runs = (store.runs or 0) + 1
<
                                                             *dbdash-callback*
`dbdash.run(args)` runs the panel's whole pipeline again (`query.sql`
template, query, `query.transform`, rows check) with `args` merged over the
current arguments, and returns the rows as `{ columns, types, rows }`; every
Lua of the panel can call it. In a push panel (|dbdash-push|) there is no
query to run: it takes the current item again through `query.transform`
with those arguments. In that run `meta.run.kind` is "callback"
("refresh" in a refresh), so the template can call back only from the
refresh: >jinja
  {% lua %}
    if meta.run.kind == "refresh" then
      store.last_week = dbdash.run({ days = 14 }).rows[1][1]
    end
  {% endlua %}
<
A callback can call back too. `meta.run.depth` is 0 in a refresh, 1 in its
callback, 2 in that one's, and so on: compare it to stop at a level. Here
the refresh and its callbacks run the query for 7, 14, 28 and 56 days (with
`days` 7), each level calling the next until depth 3: >lua
  -- query.transform
  if meta.run.depth < 3 then
    dbdash.run({ days = args.days * 2 })
  end
  if meta.run.kind == "callback" then
    return rs                       -- a callback: its own rows
  end
  -- the refresh: one row per level of its life
  local out = {}
  for _, r in ipairs(meta.runs) do
    out[#out + 1] = { depth = r.depth, days = r.args.days }
  end
  return out
<
A callback is not a refresh: no new rows on screen, no history, and
`refresh_count`, `meta.prev` and `meta.prev_ok` do not change. It runs
inside the refresh, within the query timeout, and its errors fail the
refresh. More
than `lua.max_callbacks` calls in one refresh (all levels together; each
refresh counts from 0) or nesting deeper than `lua.max_callback_depth`
(|dbdash-setup|) fails the refresh too. Each callback has a run record
(|dbdash-runs|): `meta.run.parent_id` is its caller, `meta.run.refresh_id`
its refresh, and the caller finds it in `meta.runs`.

A `lua://` query returns rows (|dbdash-result|), or any value that its
`query.transform` turns into rows. Errors name the config file and line; a
script still running at the query timeout, or when its refresh is cancelled
(|dbdash-cancel|), is stopped (loops that never call a function may only stop
then). Blocking calls such as `vim.fn.system()` freeze
the editor: use `dbdash.system()`.

Trust: Lua runs with your permissions, so a config that runs Lua (or a
script: `exec://`) is trusted before it starts. The unit is the config: one
question covers all the Lua it runs, its own (`lua://`, `luastream://`,
`exec://`, `transform`, `{% lua %}` blocks) and the files it
imports, includes or extends (`.lua` modules and templates with `{% lua %}`
blocks, found through imports, includes and extends whose target is a
quoted name). The question lists those files:
Allow, View, Deny or Not now. View shows them in one floating window: the
config (named in the title), then each imported file after a separator line
with its path; `a` allows (and starts it), `d` denies, `q` closes without
deciding. Decisions are kept in
`stdpath("state")/dbdash/trust.json` for that config and those contents: when
the config or any of the files changes, it is asked about again, and two
configs sharing a `.lua` file are asked about separately. A file with Lua
loaded while rendering that the decision does not cover (an import with a
computed path, or a file changed since the dashboard started) asks again right
away, listing all the files; until it is allowed that refresh fails, and
allowing it from the View float refreshes the panel.
`setup({ lua = { confirm = false } })` turns the question off, and
`lua = { trusted_dirs = { "~/dashboards" } }` skips it for configs under those
directories. A config cannot skip it itself.

Transforms                                                  *dbdash-transform*

Every query, of any database, goes the same way: the query, then
`query.transform` if the config has one, then the rows check
(|dbdash-result|). Results of SQL databases pass as they are; a `lua://`
script, an HTTP response or an item of a push source (|dbdash-push|) may be
anything, and the transform makes rows of it. The transform is Lua
(|dbdash-lua|: template, globals, helpers, trust) and sees:

  rs         SQL and the other databases: the result as plain data,
             `rs.columns` (names), `rs.types`, `rs.rows` (lists, nil for
             NULL); `lua://`: what the script returned; `http(s)://`: the
             response body, decoded when it is JSON (null becomes nil in
             objects and `dbdash.null` in lists), else the text
             push sources: one item (text, or the value `dbdash.emit()` or
             a request gave)
  response   (`http(s)://`) `{ status, reason, headers, body, url }`:
             header names in lower case, `body` the raw text, `url` the
             final URL after redirects
  stream     (`exec://`) "stdout" or "stderr" (|dbdash-exec|)
  params     (`webhook://`) `{ path, query, header, cookie }` and
  request    `{ method, path, operation_id, content_type, headers }`
             (|dbdash-webhook|)
  args, meta the dashboard arguments and metadata (assigning `args.x`
             sets it, |dbdash-assign-args|)
  store      the panel's table (|dbdash-store|)
  dbdash.*   the helpers, `dbdash.run()` too (|dbdash-callback|)

It returns rows in one of the shapes of |dbdash-result|; its errors (and a
value that is not rows) are reported with the phase "transform" and the
config file and line.

HTTP                                                             *dbdash-http*

`http://` and `https://` URLs call an HTTP API. The URL is the base address;
`user:password@` sends Basic authentication (|dbdash-passwords| works too).
`query.sql` (after the template) is a curl command describing the request;
its URL is a path, joined to the URL's: >yaml
  database:
    url: https://api.example.com/v1?api_key=${API_KEY}
  query:
    autoescape: true          # {{ }} values are shell-quoted words
    sql: |
      curl -X POST /search \
        -H 'Authorization: Bearer {{ args.token }}' \
        -G --data-urlencode q={{ args.keyword }} \
        --json '{"limit": 20}' -L
    transform: |
      local out = {}
      for _, it in ipairs(rs.data.items) do
        out[#out + 1] = { name = it.name, n = it.count }
      end
      return out
<
The command is read the way a shell reads it: '...' is literal, "..." takes
\" \\ \$ \`, $'...' takes C escapes (\n \t \' \xHH \uHHHH), a backslash
outside quotes escapes the next character and a backslash at the end of a
line continues it; # starts a comment at the start of a word. There are no
variables, globs or command substitution. The leading `curl` is optional;
`curl` alone GETs the URL. A request is required: an empty `query.sql` is
an error, and so is the JSON request description of earlier versions.

The URL argument is a path only: the scheme, host and port (and TLS,
passwords and timeouts) are the database URL's. The path is joined to the
URL's path as written (plain concatenation: `/v1` + `/search` is
`/v1/search`, `/v1` + `search` is `/v1search`) and may carry `?a=1`
(quote it: `curl '/items?a=1&b=2'`). Parameters in the URL other than
dbdash's own (`tls`, `fingerprint`, `ca`, `tls_host`, `connect_timeout`,
`timeout`) are sent too, then the path's, then those -G moves there.

Options, as curl's:

  -X, --request METHOD      the method (default: POST with data, else GET)
  -H, --header 'Name: v'    a header; may be repeated
  -d, --data, --data-ascii  data, joined with "&" when repeated; sent as
  --data-binary, --data-raw   application/x-www-form-urlencoded unless a
                            Content-Type header says otherwise; @file reads
                            a file next to the config (-d drops its
                            newlines; --data-raw takes @ literally)
  --data-urlencode X        X as content, =content, name=content, @file or
                            name@file, URL-encoded
  --json DATA               a JSON body: Content-Type and Accept are
                            application/json unless given
  -G, --get                 the data goes to the URL's parameters (a GET)
  -b, --cookie X            "a=1; b=2" cookies, or a Netscape cookie file
                            (no "="); '' only turns cookies on; see below
  -c, --cookie-jar FILE     write the cookies to FILE afterwards (below)
  -j                        drop session cookies when reading -b files
  -u, --user user:pass      Basic authentication (over the URL's account)
  -A, --user-agent, -e, --referer   the User-Agent and Referer headers
  -L, --location            follow redirects (not followed without it)
  --max-redirs N            at most N redirects with -L (default 50)
  -k, --insecure            https without verifying the certificate (as
                            `tls=require`)
  -m, --max-time S          seconds for the request (default:
                            query.timeout); --connect-timeout S too
  -I, --head                a HEAD request
  --url PATH                the path, as an option

Options about curl's output (-s, -S, -v, -i, -f, --fail-with-body, -g,
--compressed, --http1.1, --no-progress-meter, -#) are accepted and mean
nothing here, so a command copied from a terminal or "Copy as cURL" runs as
it is. Multipart forms (-F), -o/-O, -T, proxies (-x) and unknown options
are errors that say so.

Values from templates: write them with `| shell_quote`
(|dbdash-template-filters|), or set `query.autoescape: true` and every
`{{ value }}` becomes one shell word (|dbdash-template-autoescape|), so
`it's a test` cannot break the command or add options to it.

Cookies work as curl's cookie engine. Without -b or -c it is off: cookies
the server sets (Set-Cookie) are dropped, also across redirects. -b turns
it on: its "a=1; b=2" cookies are sent, its cookie files read (one that
does not exist has none), and what the server sets is used by the
redirects of the request (by Domain, Path, Secure and expiry; the server's
value wins over -b's of the same name). -c FILE writes all the cookies
(read and set, session cookies too) to FILE in curl's Netscape format after
the request, so a later refresh, or Neovim after a restart, reads them back
with -b: >yaml
  sql: curl /whoami -b .cookies.txt -c .cookies.txt
<-c writes only inside the config's directory (a relative path without
`..`), with permissions 600 (cookies are credentials), and a config whose
query writes a cookie file asks whether you trust it first, as Lua does
(|dbdash-lua|); -c must be in `query.sql` itself. Configs, -b files and
data files are only read.

`https` verifies the certificate and host name by default
(`tls=verify-full`, see |dbdash-tls|); `tls=require`, `pin` or -k relax
that.

The response body is the query's result: JSON (by Content-Type, or text
that starts with `[` or `{` when there is none) is decoded, anything else
stays text. It is then checked as rows (|dbdash-result|): a JSON list of
objects or `{"columns": [...], "rows": [...]}` shows directly; other JSON
and text need `query.transform`, which also gets `response`
(|dbdash-transform|).

A response other than 2xx is an error showing the status, the URL and the
start of the body (401 and 403 count as authentication errors); a redirect
without -L is one too. Compressed responses are not requested and not
supported; bodies are limited to 64 MB.

Push sources                                                     *dbdash-push*

`luastream://`, `exec://` and `webhook://` are push sources: data arrives
instead of being queried on an interval. All three work the same way:

- A producer runs: Lua code (|dbdash-luastream|), a script (|dbdash-exec|)
  or an HTTP endpoint (|dbdash-webhook|). What it writes is cut into items
  at `database.options.delimiter` (default a newline; a "\r" before it is
  dropped, empty items are skipped, items longer than `push.max_record` are
  cut there). One item is passed at a time.
- Items wait in the panel's queue (unlimited by default: a source that keeps
  sending faster than `query.transform` takes the items makes it grow; with
  `push.max_queue` set, a full queue drops the oldest). One consumer takes
  them in order, one at a time, each a run of kind "push" (|dbdash-runs|):
  `query.transform` gets the item as `rs` (text, or the value `dbdash.emit()`
  or a request gave), plus `stream`, `params` or `request` where the source
  gives them, and returns rows. Without a transform an item must be JSON
  rows (|dbdash-result|). `store`, `meta.prev`, `meta.prev_ok` and
  `meta.refresh_count` follow each item; `dbdash.run(args)` runs the
  transform on the same item with other arguments (|dbdash-callback|).
- The panel shows new data at most once per `show.interval`
  (|dbdash-interval|): the first item of a period at once, the latest of the
  others at the next one. A hidden dashboard keeps taking items and draws
  when it is shown again.
- A failed item (its transform failed, or it is not rows) shows its error;
  the source goes on and the next item replaces it.
- The source starts with the dashboard, and again with `r`, |:DbDashRestart|
  and changed arguments (`query.sql` is rendered then, with the arguments of
  that moment). Timer refreshes do not start it.
- When an `exec://` script or `luastream://` code ends, the queue is
  drained, the last result drawn and the panel stops: its header says
  "ended" (or shows the error); other panels go on, `r` starts it again.
  Stopping the dashboard stops the source (the script is killed, the port
  closed).

The panel's header shows the state ("running", "listening
127.0.0.1:8765", "ended"); |:DbDashStatus| the items received, processed,
queued, dropped and cut, and the requests a webhook refused.

Lua stream                                                  *dbdash-luastream*

`luastream://`: `query.sql` is Lua, like |dbdash-lua|, whose output is the
data: text written with `print()` or `io.write()` is cut into items, and
`dbdash.emit(value)` passes one item as it is (a table, for example). A value
the code returns is the last item; it ends when the code returns. >yaml
  database:
    url: "luastream://"
    options: { cwd: "logs", delimiter: "\n" }
  query:
    sql: |
      for line in io.lines("events.log") do print(line) end
<
It has no timeout: it runs until it returns or is stopped. Code that runs
longer than the query timeout without waiting (`dbdash.sleep()`,
`dbdash.checkpoint()`, a query, a command) is stopped, as it would freeze
Neovim.

`options.cwd` is its directory (default: the config file's; relative to
it). Lua runs inside Neovim, so instead of changing the process's directory,
`io.open`, `io.lines`, `dofile` and `loadfile` read relative paths from
there and `io.popen`, `os.execute` and `dbdash.system()` run commands there;
`dbdash.cwd` is its path. Neovim's own directory does not change.

Script                                                           *dbdash-exec*

`exec://`: `query.sql` is a script; its output is the data. Everything else
is in `database.options`: >yaml
  database:
    url: "exec://"
    options:
      interpreter: ["bash", "-c"]   # default sh -c (cmd /d /s /c on Windows)
      capture: both                 # stdout (default), stderr or both
      delimiter: "\n"
      ok_codes: [0, 1]              # exit codes that end normally (default 0)
      cwd: "~/logs"                 # default: the config file's directory
      env: { LANG: C }              # added to Neovim's environment
      stdin: "..."                  # written to the script, then closed
  query:
    sql: tail -n 0 -F app.log
<
The script is the interpreter's last argument (`["python3", "-c"]`,
`["pwsh", "-Command"]` and `["nvim", "--clean", "-l", "run.lua"]` work too).
Each item knows its `stream` ("stdout" or "stderr"; the two are separate
pipes, so lines of one may come before earlier lines of the other). An exit
code not in `ok_codes` ends the panel with an error showing the code and the
end of stderr. Stopping sends SIGTERM, and SIGKILL after 2 seconds.
Arguments written into the script (`{{ args.file }}`) are text in it: quote
them for the shell, or read them in the script some other way.

Webhook                                                       *dbdash-webhook*

`webhook://host:port/path` listens on its own port (host defaults to
127.0.0.1; port 0 takes any free one, shown in the header). `query.sql` is an
OpenAPI 3.1 document (YAML or JSON; 3.0 is accepted too) describing what it
accepts; the document's paths are appended to the URL's path as written
(`/api` and `/orders/{id}` serve `/api/orders/{id}`). Without a document it
takes POST and PUT of anything at the URL's path. >yaml
  database:
    url: "webhook://127.0.0.1:8765/api"
    options:
      tokens: { bearer: "${ORDERS_TOKEN}" }
  query:
    sql: |
      openapi: 3.1.0
      info: { title: orders, version: "1" }
      security: [ { bearer: [] } ]
      paths:
        /orders/{shop}:
          post:
            parameters:
              - { name: shop, in: path, required: true,
                  schema: { type: string, enum: [bj, sh] } }
              - { name: limit, in: query,
                  schema: { type: integer, default: 10 } }
            requestBody:
              required: true
              content:
                application/x-ndjson:
                  schema: { $ref: "#/components/schemas/Order" }
                application/json:
                  schema: { type: array }
            responses: { "202": { description: queued } }
      components:
        schemas:
          Order:
            type: object
            required: [id]
            properties: { id: { type: integer }, amt: { type: number } }
        securitySchemes:
          bearer: { type: http, scheme: bearer }
<
What the document can say:

- paths with templates (`{name}`, one segment; concrete paths win), every
  method, path item parameters merged with the operation's;
- parameters in path, query, header and cookie, with `schema` (types are
  converted, defaults filled in), every `style` and `explode` (form, simple,
  label, matrix, spaceDelimited, pipeDelimited, deepObject), `required`,
  `allowEmptyValue` and `content` (e.g. JSON in a query parameter);
- `requestBody` with media types chosen by Content-Type (exact, then
  `type/*`, then `*/*`), forms with `encoding`, multipart;
- `security` (http bearer, http basic, apiKey in a header or a cookie;
  requirements are alternatives, the schemes of one are all needed) with
  the credentials in `database.options.tokens` by scheme name (a string,
  "user:password" for basic, or a list; `${NAME}` reads the environment);
- the first 2xx response is the reply, with its `example` as the body
  (else 202 and `{"queued": N}`);
- `$ref` in the document and to files next to it (`schemas.yaml#/Order`).

Schemas are JSON Schema 2020-12 (OpenAPI 3.1's; formats date-time, date,
time, email, uri, uuid, ipv4, ipv6 and hostname are checked, `pattern` is
an ECMA-262 regular expression).

Items, by the request body's media type:

  application/x-ndjson, application/jsonl, application/json-seq,
  text/plain, text/csv, text/event-stream (and options.stream_types)
               cut at the delimiter: one item per piece, each checked
               against the schema (JSON ones decoded)
  other JSON   the decoded body is one item
  forms        the fields are one item (a mapping)
  no body      the parameters are one item (a mapping)

`query.transform` also gets `params` (`{ path, query, header, cookie }`,
converted) and `request` (`{ method, path, operation_id, content_type,
headers }` without the credential headers). A request that does not fit gets
an `application/problem+json` reply and gives no items: 400 (what and
where), 401 (with WWW-Authenticate), 403, 404, 405 (with Allow), 408, 413,
415. When a streamed body has a bad item, the items before it are kept.

Options: `tokens`, `delimiter`, `stream_types`, `max_body` (default 10MB),
`max_connections` (16), `timeout` (10s to send the headers and each part of
the body), `allowed_origins`, `allowed_hosts` (|dbdash-webhook-security|).

Webhook security                                     *dbdash-webhook-security*

A webhook follows MCP's rules for HTTP endpoints:

- It listens on 127.0.0.1 unless the URL names another address; then every
  operation must have a `security` requirement, or it does not start.
- Credentials go in headers or cookies only: an apiKey in the query string is
  refused (URLs end up in logs). They are compared in constant time and never
  shown in `request`, `params`, errors or replies.
- The Host header must be the listening address, localhost or one of
  `allowed_hosts`, and a request with an Origin header (browsers send one)
  must come from one of `allowed_origins` (none by default): this stops
  web pages from reaching the port through DNS rebinding. Requests without
  an Origin (curl, scripts) are not affected.
- Bodies, connections and slow requests are limited (`max_body`,
  `max_connections`, `timeout`).

TLS                                                               *dbdash-tls*

Modes:

  require      encrypt (TLS 1.3, or 1.2 when the server has no 1.3) without
               checking the certificate: stops passive eavesdropping but not
               a man in the middle.
  pin          `&fingerprint=sha256:AB:CD:...`: the leaf certificate must
               have that SHA-256 fingerprint. On a mismatch the error shows
               the fingerprint the server presented.
  verify-ca    validate the certificate chain against the system CA store
               (or `&ca=bundle.pem`, e.g. a cloud provider's CA bundle).
  verify-full  verify-ca plus the host name: subjectAltName DNS names
               (left-most `*.` wildcards) and IP addresses; certificates
               without subjectAltName fall back to the common name.

pin, verify-ca and verify-full also require the server to prove possession of
its key (CertificateVerify). Chains may use RSA (PKCS#1 v1.5, PSS) and ECDSA
P-256/P-384 signatures; SHA-1 signatures are rejected; revocation (CRL/OCSP)
is not checked. The system store is read from the usual bundle files on
Linux/macOS/BSD. On Windows the trusted roots are the "Trusted Root" and
"Third-Party Root" certificate stores; certificates of the "Intermediate"
store only complete chains. Windows installs many roots only when some program
first needs them, so if verify-ca fails there with an unknown CA, pass the CA
with `ca=` (`:checkhealth dbdash.postgres` shows how many roots were found).

Get a server's fingerprint with:
>sh
  openssl s_client -connect host:5432 -starttls postgres </dev/null \
    2>/dev/null | openssl x509 -noout -fingerprint -sha256
<
PostgreSQL, MySQL and SQL Server negotiate TLS on their normal port; Redis,
MongoDB and Cassandra start TLS right away (use the server's TLS port;
`rediss://` and MongoDB's `tls=true` imply `require`). `https://` starts TLS
right away and defaults to `verify-full` (|dbdash-http|).

Supported: TLS 1.3 (X25519 or secp256r1; AES-128-GCM or ChaCha20-Poly1305)
and TLS 1.2 (ECDHE or RSA key exchange; AES-GCM, ChaCha20-Poly1305 or
AES-CBC with HMAC; encrypt-then-MAC and extended master secret when the
server supports them). TLS 1.0/1.1, renegotiation and session resumption
are not supported.

Known risk: the cryptography is pure Lua and not constant-time, so timing
side channels exist in theory. This is accepted for a client that
periodically reads dashboard data; prefer `pin` over `require` on untrusted
networks.

Oracle is not supported.

9. HIGHLIGHTS                                              *dbdash-highlights*

All groups link to standard groups by default:

  DbDashTitle DbDashBorder DbDashHeader DbDashNull DbDashMuted DbDashNumber
  DbDashAxis DbDashLabel DbDashError DbDashWarn DbDashCountdown
  DbDashArgName DbDashArgValue DbDashArgLocal DbDashDescIcon
  DbDashSeries1 ... DbDashSeries8   chart series colors (palette "theme")
  DbDashStatValue (Number), DbDashUp (DiagnosticOk), DbDashDown
  (DiagnosticError)                 stat value and its change

Sidebar: `DbDashSidebarDir` (directory names and their ▸/▾, links to
`Directory`), `DbDashSidebarRunning` (● of running dashboards, links to
`DiagnosticOk`), `DbDashSidebarPaused` (◐ of paused ones, links to
`DiagnosticWarn`), `DbDashSidebarIdle` (○, links to `Normal`). With
`sidebar.cursorline = "name"` the sidebar window's cursor line uses
`DbDashSidebarCursorLine` (empty) instead of `CursorLine`, and
`DbDashSidebarCursor` (underline) marks the name on the cursor line without
the ●/◐/○ marker: a terminal draws an underline in the text color, so with an
underlined CursorLine the green ● leaves a green piece in the line.

`DbDashTrustFile` (links to `Title`) is the separator line before each
imported file in the View float of the trust question (|dbdash-lua|).

Colors in configs may be hex ("#3498db"), names ("blue", "bold blue"),
or existing highlight groups ("DiagnosticOk").

10. LUA API                                                       *dbdash-api*

require("dbdash").start({config}, {tokens})   start a dashboard
require("dbdash").stop({config})              stop it
require("dbdash").query({url}, {query}, {opts}, {callback})
    run a query through the data layer; callback(err, resultset) is called
    once, on the main loop. Returns a handle: `handle:cancel(reason)` stops
    the query (|dbdash-cancel|). Push sources (|dbdash-push|) cannot be
    queried this way: they run as a panel's stream.
require("dbdash.db").register({driver})        add a data source
    {driver} has a `name`, `schemes` (default { name }) and one of:
    - `connect(info)`: a database. It returns a connection with
      `execute(query, opts)` (a result set), `close()` and optionally
      `server_version()`; dbdash queries it once per period, with timeouts
      and backing off after failures. Optionally `cancel(conn, info)` stops
      the running query on the server (|dbdash-cancel|).
    - `produce(info, query, ctx)`: a source that sends data. `ctx.emit(value)`
      passes one item, `ctx.writer(delimiter)` returns a function whose text
      is cut into items, `ctx.set_status(text)` and `ctx.on_stop(fn)`; it
      runs until it returns.
    Optionally `options`: the `database.options` it reads, by name, each a
    type name ("string", "integer", "boolean", "map", "list") or a function
    returning an error message; a config with another option is an error.
    Also `dialect` (how template values are written,
    |dbdash-template-dialects|),
    `parse_url(info)` and `query_optional` (a config may leave `query.sql`
    out). A driver without `name`, or with both or neither of `connect` and
    `produce`, is an error. The types are in lua/dbdash/db/types.lua.

                                                        *dbdash-session-state*
require("dbdash").mksession({file})
    Write the argument values of running dashboards that differ from their
    defaults (command line, edited or entered) to {file} as JSON, like
    :mksession writes the windows. Returns true, or false and an error.
require("dbdash").load_session({file})
    Load values written by mksession(), like :source of a session: running
    dashboards refresh with them, the others get them when they start (call
    it after sourcing the session). A missing {file} is not an error;
    unknown arguments and invalid values are skipped.

Sessions restore dashboards with default arguments; when to save and load
the changed ones is up to your session setup, e.g. next to the session
file: >lua
  -- after :mksession {file}
  require("dbdash").mksession(file .. ".dbdash")
  -- after :source {file}
  require("dbdash").load_session(file .. ".dbdash")
<
